Executive summary

22Total findings
5Critical / release blockers
11High severity
6Medium / structural
Recommendation: do not merge or use the branch for trusted scientific results until at least F01–F05 are fixed and exercised by integrated serial and MPI tests. The current formula-level tests are insufficient, and in the default Release build their assert() checks are disabled.

The branch introduces a substantially improved architecture—explicit radiation packet state, DDMC face data, collective metadata exchange, Compton abstractions, observers, and polarization support. The highest-risk defects are concentrated at representation and process boundaries: DDMC↔IMC conversion, cross-rank ghost metadata, moving-frame Compton events, and binary decoding.

The implementation agent should resist local one-line patches that leave the state machine fragmented. The safest approach is to introduce centralized transition helpers and executable invariants first, then fix physics and MPI semantics around those helpers.

Scope, evidence, and caveats

This report is based on a static inspection of the rich_features branch and its comparison with main. The reviewed change set was six commits ahead of the observed main snapshot and added roughly 4,400 lines across RadiationIMC.hpp, DDMC support, packet state, Compton, observers, polarization, CMake, and three focused tests.

Important caveat: no local build, sanitizer run, MPI execution, regression suite, or numerical convergence study was performed as part of this review. “High confidence” means the issue follows directly from the inspected control/data flow; “Medium” means the concern depends on intended physics or an external contract that should be confirmed.

Snapshot caveat

The branch may move after this report is generated. File links intentionally point to the branch for convenience, while the implementation agent should record the exact head SHA before changing code and re-check whether a finding has already been addressed.

External contracts that must be verified

  • MadVoro meanings and ordering guarantees for duplicated points, sent points, ghost indices, and stable/self indices.
  • The intended units and frame of frequencies, packet weights, and Compton kernel matrix entries.
  • Boundary-manager semantics for reflected, escaped, removed, and re-emitted packets.
  • Whether DDMC residents are intended to persist across census or be reconstructed as transport packets.
  • The exact scientific derivation intended for moving-interface factors, momentum feedback, and accelerated polarization closure.

Non-goals

This review does not claim that unmentioned code is correct, nor does it constitute validation of the DDMC/Compton discretization against the original RICH implementation or published benchmarks.

DDMC ghost metadata appears to use the wrong MadVoro communication maps

Primary files: radiation/ddmc/DDMCGhostExchange.hpp · utils/MpiExchangeGrid.hpp

Static evidence

  • ExchangePointMetadata() builds outgoing messages from GetSentProcs()/GetSentPoints(), then places received entries into GetGhostIndeces().
  • STORM’s existing MPI_exchange_data(..., ghost_or_sent=true) contract uses GetDuplicatedProcs()/GetDuplicatedPoints() for ghost exchange; GetSent* is used by the alternate migration path.

Why it matters

Cross-rank DDMC eligibility, diffusion coefficients, cutoffs, velocities, and stable IDs may be missing, assigned to the wrong ghost slots, or rejected by count checks. This can silently convert DDMC–DDMC faces into IMC interfaces and can produce rank-dependent physics.

Suggested implementation

Retain the collective Alltoallv structure, but build each destination payload from GetDuplicatedProcs() and GetDuplicatedPoints(). Validate that each incoming source count exactly matches the corresponding GetGhostIndeces() list. Add a two-rank test with asymmetric ownership and at least one rank owning zero real cells.

Acceptance criteria

  • The test reproduces the same ghost metadata as MPI_exchange_data(..., true).
  • Cross-rank and same-rank face classifications are identical for an equivalent mesh partition.
  • No count mismatch occurs when a peer has zero outgoing entries.
Source locations reviewed
  • radiation/ddmc/DDMCGhostExchange.hpp (40–223)
  • utils/MpiExchangeGrid.hpp (13–49)

DDMC stochastic upscatter leaves an above-cutoff packet resident in DDMC

Primary files: radiation/RadiationIMC.hpp

Static evidence

  • The stochastic group-exit branch samples a frequency from groups at or above groupCutoff, then sets DDMCMode, DDMCCellResident, and DDMCComovingFrame.
  • On the next call, the above-cutoff check returns false without clearing DDMC state or converting the packet to the lab frame; the caller then continues through ordinary IMC transport.

Why it matters

A packet can be transported as an IMC ray while its frequency and weight remain comoving-frame quantities, its direction is only a DDMC representative direction, and isDDMC() remains true. Interface admission and momentum/energy accounting can become incorrect.

Suggested implementation

Make every stochastic group-exit event a real DDMC-to-transport conversion. Sample the upper-band frequency, reconstruct a transport direction, finalize accelerated polarization history, transform to the lab frame when required, clear DDMC state, and return NO_CELL_MOVE. Centralize this in one exitDDMCToTransport() helper shared by cutoff, census, fallback, and interface exits.

Acceptance criteria

  • Immediately after group exit, isDDMC(), isResident(), and isComoving() are false.
  • The outgoing packet is lab-frame and has a finite physical direction of magnitude c.
  • A one-cell multigroup test shows no packet above groupCutoff remaining resident.
Source locations reviewed
  • radiation/RadiationIMC.hpp (DDMC upscatter and tryDDMCStep sections)

DDMC fallback paths do not guarantee restoration of a valid IMC packet

Primary files: radiation/RadiationIMC.hpp · particle/RadiationTransportState.hpp

Static evidence

  • tryDDMCStep() has several return-false paths for invalid cutoff state, failed eligibility/gates, and inconsistent state.
  • The caller treats false as permission to continue through the normal IMC path. The cleanup branch for an ineligible resident is not reliably reached because tryDDMCStep() is called only when the current cell is eligible.

Why it matters

Stale resident/comoving flags or representative DDMC directions can leak into IMC transport. The error may be intermittent because it depends on a dynamically changing eligibility or cutoff state.

Suggested implementation

Adopt a strict contract: false means “packet is already a valid lab-frame IMC packet.” For every resident fallback, either throw a state-invariant error or call the centralized DDMC exit helper before returning false. Add debug assertions in step() after a false return.

Acceptance criteria

  • Every false return from tryDDMCStep() leaves a non-DDMC lab-frame packet.
  • No packet reaches getIntersectionDetails() with DDMCCellResident set.
  • Eligibility changes between timesteps do not corrupt carried census packets.
Source locations reviewed
  • radiation/RadiationIMC.hpp (tryDDMCStep and step dispatch)
  • particle/RadiationTransportState.hpp (56–75)

Moving-medium Compton events appear to leave frequency and direction in the wrong frame

Primary files: radiation/RadiationIMC.hpp · radiation/Compton.hpp

Static evidence

  • The source group and interaction opacity are selected from a Doppler-shifted frequency.
  • The Compton event samples a target-group frequency and new direction, but the later comoving-to-lab path is explicitly skipped when isComptonScatter is true.

Why it matters

In moving media, the next transport step can interpret a material-frame target frequency as a lab-frame frequency. Energy and momentum exchange can be inconsistent with the packet’s actual lab-frame four-momentum change.

Suggested implementation

Execute the whole Compton event in the cell-comoving frame: transform incoming packet; select source/target group; sample outgoing energy and direction using the Compton kernel; calculate material energy/momentum exchange; transform the outgoing packet back to lab. Add a v=0 parity test and a moving-cell round-trip test.

Acceptance criteria

  • Zero-velocity behavior is unchanged.
  • A lab→comoving→event→lab test closes energy and momentum within tolerance.
  • Reversing the cell velocity gives the expected Doppler symmetry.
Source locations reviewed
  • radiation/RadiationIMC.hpp (computeDopplerShift, scattering event)
  • radiation/Compton.hpp (19–68)

MPI byte decoding invokes undefined behavior through alignment and object-lifetime violations

Primary files: radiation/ddmc/DDMCGhostExchange.hpp

Static evidence

  • Received bytes are stored in vector<std::byte> and reinterpreted as const T* before dereference.
  • vector<std::byte> does not guarantee alignment for arbitrary T, and in C++17 the buffer does not contain live T objects.

Why it matters

The code may work on x86 but fail under strict-alignment architectures, sanitizers, aggressive optimization, or a different compiler. Failures can present as corrupted ghost data rather than an obvious crash.

Suggested implementation

Decode every element with std::memcpy into a properly aligned local T, or exchange a vector<T> with an appropriate contiguous MPI datatype. Keep the trivially-copyable requirement. Apply the same correction to metadata exchange and contribution reduction.

Acceptance criteria

  • UBSan/alignment sanitizer reports no issue.
  • Round-trip tests pass for double, size_t, integer flags, and PointT.
  • The decoded values are bitwise identical to the sent values.
Source locations reviewed
  • radiation/ddmc/DDMCGhostExchange.hpp (161–223 and reduction receive loop)

Enabling Compton suppresses all ordinary elastic scattering

Primary files: radiation/RadiationIMC.hpp · radiation/Compton.hpp

Static evidence

  • elasticScatteringOpacity is assigned zero whenever withCompton is true.
  • The Compton abstraction describes a separate group-changing operator rather than a replacement for the ordinary opacity model.

Why it matters

A model that requires both ordinary scattering and Compton redistribution loses all ordinary scattering interactions. This changes mean free paths, angular redistribution, polarization, and energy deposition.

Suggested implementation

Calculate elastic scattering opacity independently and add it to effective absorption and Compton opacity. If a kernel already includes ordinary scattering, expose an explicit capability/configuration flag rather than silently zeroing the opacity.

Acceptance criteria

  • A test with nonzero elastic and Compton rates observes both event types statistically.
  • Disabling Compton recovers the original elastic-only result.
Source locations reviewed
  • radiation/RadiationIMC.hpp (transport opacity assembly)
  • radiation/Compton.hpp (19–31)

The exposed angle-dependent Compton option is not implemented by the current API

Primary files: radiation/RadiationIMCParameters.hpp · radiation/Compton.hpp · radiation/RadiationIMC.hpp

Static evidence

  • comptonAngleDependent defaults to true.
  • The kernel returns group matrices and scalar corrections but has no conditional angular-event sampler.
  • The event uses ordinary opacity-model direction sampling and thermal in-group frequency sampling.

Why it matters

Users can believe Klein–Nishina or another angle-energy coupling is active when the implementation only performs coarse group redistribution with unrelated direction sampling.

Suggested implementation

Either reject comptonAngleDependent=true until implemented, or extend ComptonKernelModel with an event sampler returning target energy, direction, packet-weight factor, and material four-momentum exchange. Avoid using SampleThermalEnergyInGroup for a Compton conditional spectrum unless formally justified.

Acceptance criteria

  • Unsupported configurations fail at construction with a precise message, or a kernel-provided angular sampler is invoked and tested.
  • A monoenergetic scattering test reproduces the expected energy-angle relation.
Source locations reviewed
  • radiation/RadiationIMCParameters.hpp (34–42)
  • radiation/Compton.hpp (47–68)
  • radiation/RadiationIMC.hpp (Compton scattering event)

Per-group Compton Fleck corrections are collapsed to one global minimum

Primary files: radiation/RadiationIMC.hpp · radiation/Compton.hpp

Static evidence

  • ComptonKernelResult supplies fleckCorrection as a group array.
  • precomputeComptonData() takes the minimum across groups and fills every group with the same modified value; transport reads one scalar fleck.

Why it matters

Most groups can be over- or under-implicitized, affecting stability, source terms, and redistribution rates.

Suggested implementation

Compute modifiedFleck[g] = clamp(cellFleck * kernelFleck[g], 0, 1) and use modifiedFleck[sourceGroup] during transport. Keep a scalar only for summary diagnostics if needed.

Acceptance criteria

  • A synthetic kernel with distinct group corrections produces distinct transport Fleck factors.
  • Single-group behavior remains unchanged.

DDMC census resamples from the full thermal spectrum instead of the resident band

Primary files: radiation/RadiationIMC.hpp

Static evidence

  • At census the code clears DDMC state and calls GetThermalEnergy using all energy boundaries.
  • A multigroup DDMC resident represents only groups below groupCutoff.

Why it matters

A low-band resident can be moved into an upper transport group at every census without a physical group-exit event, introducing artificial spectral redistribution.

Prefer preserving DDMC residence across census. If the manager requires an IMC packet, reconstruct frequency from the conditional Planck distribution over [0, groupCutoff), not over all groups.

Acceptance criteria

  • No census-only test produces frequencies at or above groupCutoff.
  • Band energy is conserved across repeated census operations.

bypassCellID is set but not enforced when DDMC admission is reconsidered

Primary files: radiation/RadiationIMC.hpp · particle/RadiationTransportState.hpp

Static evidence

  • Invalid moving-interface conditions set bypassCellID and move the packet into the target cell as IMC.

A packet can enter DDMC in the exact cell that was intentionally bypassed, for example after a scattering or after moving far enough inward.

  • The bypass clears after crossing into the next cell.

The moving-interface weight correction has no finite variance/weight cap

Primary files: radiation/ddmc/DDMCWollaegerInterface.hpp · radiation/RadiationIMC.hpp

Static evidence

  • The kernel grows strongly near grazing incidence and is tabulated down to very small mu.
  • The admitted packet weight is multiplied directly by MovingFactor; only nonfinite or nonpositive values are rejected.

Why it matters

Finite but very large weights can cause catastrophic variance, negative material-energy excursions, or later overflow.

Suggested implementation

Introduce a documented maximum correction. Above it, either bypass DDMC or perform unbiased packet splitting with bounded child weights. Record max factor, bypass count, and split count.

Acceptance criteria

  • A grazing-incidence stress test cannot create a packet above the configured bound.
  • Energy remains unbiased in a large-sample interface test.

Observer handling can count the same spherical crossing repeatedly

Primary files: radiation/SphericalObserver.hpp · radiation/RadiationIMC.hpp

Static evidence

  • After recording a crossing, RadiationIMC moves the packet to crossingPoint minus the outward direction times epsilon, placing it back inside the sphere.
  • The observer then finds another positive outward root unless its time epsilon happens to hide the nudge.

Why it matters

Observer energy and crossing counts may be multiplied by repeated zero-distance events. The behavior depends on radius, remaining time, and floating-point scale.

Suggested implementation

Nudge the packet outward, not inward, or record a surface-crossed state that suppresses immediate duplicate hits. Add a test that continues the same packet for several steps and asserts exactly one crossing.

Acceptance criteria

  • One outward ray produces one record.
  • A tangent/grazing ray does not oscillate around the surface.
  • No near-zero observer event loop occurs.
Source locations reviewed
  • radiation/SphericalObserver.hpp (100–145)
  • radiation/RadiationIMC.hpp (observer event branch)

Polarization observer Q/U tallies are not weighted by packet energy

Primary files: radiation/SphericalObserver.hpp

Static evidence

  • Ordinary observer energy uses record.weight.
  • The polarization accumulation adds rotated normalized q/u directly, without multiplying by record.weight.

Why it matters

Packets with very different weights contribute equally to Q and U, and negative-weight packets get the wrong sign. Reported polarization fractions are therefore invalid.

Suggested implementation

Accumulate energy-weighted Stokes values: Q += weight * rotatedQ and U += weight * rotatedU. Define whether I is signed net energy or a separate positive-intensity estimator, and derive reported fractions consistently.

Acceptance criteria

  • Doubling packet weight doubles Q and U.
  • A positive and equal negative packet cancel.
  • The existing nonzero-only test is replaced with exact weighted expectations.
Source locations reviewed
  • radiation/SphericalObserver.hpp (147–175 and 285–299)

The reciprocity diagnostic excludes cross-rank DDMC faces

Primary files: radiation/RadiationIMC.hpp · tests/DDMCMathTests.cpp

Static evidence

  • The check only compares a reverse face when the target index is locally owned.

A fully reflecting cell is disabled for DDMC merely because it has no spatial leakage

Primary files: radiation/RadiationIMC.hpp · radiation/ddmc/DDMCTypes.hpp

Static evidence

  • Cells with totalLeakRate <= 0 are marked ineligible and face leaks are cleared.
  • A cell surrounded by reflecting faces may still support absorption, census, group exit, and moving-medium evolution.

Why it matters

This is primarily an acceleration loss rather than an obvious bias, but it can produce large performance discontinuities and leaves reflecting face support underused.

Suggested implementation

Allow zero-spatial-leak DDMC cells when another event rate is nonzero. The event sampler can choose census/group-exit/absorption evolution without spatial movement. Confirm the intended physics before changing eligibility.

Acceptance criteria

  • A reflecting-box test remains in DDMC and conserves energy.
  • A true zero-event cell does not create an infinite event loop.
Source locations reviewed
  • radiation/RadiationIMC.hpp (face refresh and eligibility)
  • radiation/ddmc/DDMCTypes.hpp (FaceKind and CellData)

Numerical validation

  • Energy closure: material + radiation + escaped + signed residual source, using both global and per-cell ledgers.
  • Momentum closure for moving-medium Compton and DDMC momentum feedback.
  • Partition invariance: same problem on 1, 2, and 4 ranks with statistically compatible tallies.
  • Algorithm parity: DDMC disabled must reproduce baseline IMC; Compton disabled must preserve ordinary scattering behavior.
  • Convergence with packet count, timestep, group count, and DDMC optical-depth thresholds.

Ledger invariants

  • Packet weight is signed energy in one clearly documented frame at every program point.
  • Every frame transformation updates frequency, weight, direction, and polarization basis together.
  • A boundary escape is recorded once and only once, after the boundary outcome is known.
  • Observer Q/U are energy-like quantities; normalized q/u remain packet-local fractions.
  • Every DDMC spatial crossing contributes consistently to source and target momentum tallies, including remote targets.

Definition of done for the implementation agent

  1. All critical findings F01–F05 are fixed with tests that fail on the old branch and pass on the new code.
  2. No Release test relies exclusively on assert().
  3. Serial and MPI builds pass with new features both enabled and disabled.
  4. At least one two-rank DDMC test crosses a partition boundary and verifies metadata, packet migration, pending flux, and reciprocity.
  5. Compton tests demonstrate coexistence with ordinary scattering and correct moving-frame energy/momentum accounting.
  6. Observer tests demonstrate exactly-once crossing, signed energy closure, correct boundary escape accounting, and energy-weighted Stokes values.
  7. Sanitizers and compiler warnings are clean for the new code where the platform supports them.
  8. Existing STORM regression examples remain statistically consistent when all new features are disabled.
  9. Any intentionally deferred item is rejected by validation rather than silently exposed as an apparently functional option.
  10. Documentation states supported feature combinations, frames/units, estimator meanings, and known limitations.
Implementation discipline: make small commits grouped by invariant or subsystem, not one monolithic patch. Each commit should include the regression test that proves its behavior.
