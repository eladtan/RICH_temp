## How to interpret runtime estimates

The user requested a runtime contribution for every idea. The percentages in this note are **unmeasured planning ranges for reduction of complete MadVoro build wall time**, not promises and not reductions of complete hydrodynamics runtime. They apply only if the target work appears on the slowest-rank critical path. Case C means local Delaunay/tree/geometry computation is a substantial share of build time. Case L means small local meshes and MPI latency/progress dominate. A proposal can produce 0% or a regression when its precondition is absent; validate each independently. Do not add the percentages: proposals overlap (especially cache reuse, dirty lists, geometry threading, and build avoidance).

Replace a planning range with `saved_fraction = phase_fraction * (1 - 1 / phase_speedup)` after measuring the target phase on the critical path. For example, improving a 12% phase by 2x saves 6% of build wall time, speedup 1/0.94 = 1.064x. To translate to RICH runtime, multiply saved build fraction by the measured fraction of complete RICH runtime spent in MadVoro, then account for movement/load-balancing side effects.

| ID | Implementation idea | C: build-time reduction | L: build-time reduction | Decision precondition |
|---|---|---:|---:|---|
| G0 | Fix partial-build indexing before pursuing partial-build speedups | 0% on current full builds | 0% on current full builds | Correctness prerequisite; benefit belongs to G10 |
| G1a | Avoid the full `predicatePoints` copy per BuildExtra | 0-3% | 0-1% | Count copied bytes and BuildExtra batches |
| G1b | Incrementally maintain exactly equivalent lattice summary | 1-10% | 0-4% | Lattice scans are >=2% and many small append batches occur |
| G2 | Reuse valid cached tetra circumcenters in final Voronoi pass | 1-10%; 5-20% in fallback-heavy geometry | 0-3% | Significant already-valid cache hit rate in final pass |
| G3 | Deduplicate dirty tetra IDs before adjacency processing | 1-6% | 0-2% | New-tetra enqueue count substantially exceeds unique count |
| G4 | Replace hot free-tetra flat_set updates with explicit occupancy/free list | 1-8% | 0-2% | Profile shows flat_set shifts/lookups and free set is nontrivial |
| G5 | Remove finder point copy and intermediate range-result allocation | 1-6% | 0-3% | Many local queries or large copied local point arrays |
| G6 | Preserve inner capacities and avoid constructing excess face slots | 1-5% | 0-2% | Allocations/memory initialization are material |
| G7 | Reuse Hilbert tables and remove full-array helper copies | 1-8% | 0-3% | Hilbert setup/normalization are material; most useful for many small batches |
| G8 | Deduplicate attempted degenerate faces and reuse cleanup scratch | 0-3% typical; 2-10% degenerate/high-valence | 0-2% | Repeated rejected fans / heap spills measured |

These wide intervals describe different workload regimes. No estimate is a measured result. G10 should not appear as an expected gain for moving hydrodynamic meshes; exact equality commonly fails there. G9 ranges are not free gains under fixed total core counts and must be evaluated as rank/thread configurations.

## G0. Partial builds currently have inconsistent indexing: resolve before performance work

**Observed code:** `UpdatePointsTree` loops to `allMyPoints.size()` but reads `activePoints[pointIdx]` at V:2137-2141. A genuine subset has fewer active points than all points. The serial `BuildPartially` repeats the same mismatch at V:4176-4180. Serial map construction writes `indicesInAllMyPoints[pointIdx] = pointsCounter` at V:4103-4107, whereas parallel preparation writes `indicesInAllMyPoints[new_points.size()] = pointIdx` at V:2055-2057 and consumers such as `UpdateRadiuses` V:3207-3212 interpret `.first` as build-local index and `.second` as all-local index. Full identity masks hide both problems.

**Required contract:** `allMyPoints[k]` is coordinate of local physical point k; `activePoints[j]` is build-local active point j; `indicesInAllMyPoints[j] == k` maps build-local j to physical k. The all-point tree must contain allMyPoints coordinates indexed by k. The active-point tree must contain activePoints coordinates indexed by j. Fix both serial and parallel helpers according to this explicit contract; eliminate duplicated tree-construction code so it cannot diverge again. Validate every index before changing any loops to be faster. Tree aliasing (`myPointsTree = allMyPointsTree`) is allowed only if the actual index mapping is identity, not merely equal size; a full permutation has equal size but different build-local indices.

**Test:** 32-128 points, proper subset with sparse/nonmonotonic indices, empty subset, full identity mask, full permutation, partial builds after point migration, insertion/deletion/reorder. ASan/UBSan run on genuine subsets; compare active-cell geometry with full-build geometry where inactive ghosts complete active cells. Verify `getPoint` and nearest-tree indices resolve to the intended physical point. Existing serial map direction must be fixed before using it to validate another change.

**Runtime estimate:** 0% direct expected improvement for full builds; a prerequisite for G10. Do not claim a crash fix is a performance optimization.

## G1. Remove repeated whole-point copying/scanning in BuildExtra without changing predicate semantics

**Observed code:** D:706-713 allocates a new `std::vector<PointT> predicatePoints`, reserves old non-bounding points plus incoming count, copies original local points, copies all previously inserted extras, copies incoming batch, then constructs `LatticePredicateScope`. This happens for every nonempty `BuildExtra`. At D:715 incoming points are separately appended to `points_`. `BuildExtraTracked` V:3117-3125 wraps this. Call sites include self ghosts V:3437, remote big queries V:3474, remote small queries V:3489, prior-build ghosts V:3646, and mirrors V:3800. Therefore one ghost iteration can cause multiple whole-point copies and scans. Count calls and sizes rather than assuming one call per iteration.

**Complexity evidence:** With N original points, batches b1..bk, and cumulative B_i, copying alone is Theta(sum_i(N+B_i)); for equal batches b it is Theta(k*N + b*k^2). The actual Delaunay insertions can still dominate; the sum formula is not an overall algorithmic complexity claim.

**Scope correctness:** P:60-125 checks at least 8 points, exact conversion of coordinates to a fixed dyadic integer grid, a common gcd of coordinate differences, a power-of-two gcd, and span/divisor <=255 on all axes. It excludes the four artificial bounding points by construction. The scope sets thread-local predicate state and restores the previous state on destruction (P:128-131). D:718-719 shuffles insertion order only when that combined scope is active. Do not construct a scope only from incoming points; older off-grid points must disable the shortcut too. Do not keep `active` sticky: an active set can become inactive after appends, and an inactive set caused by non-power-of-two gcd or large span can potentially become active when the gcd changes. A failed coordinate representation remains failed under append, but a generic `inactive` state does not carry enough information.

**G1a exact staged implementation:** Add a no-copy constructor/factory that visits a fixed sequence of three disjoint ranges: `points_[0:Norg_)`, `points_[Norg_+4:points_.size())`, and incoming points. A templated visitor is sufficient; do not require C++20 span if project uses C++17. Preserve point order, first point anchor, total count, early rejection, min/max values, and all numerical comparisons. Build this summary before `points_.insert`, so vector growth cannot invalidate iterators. The iterator/view is transient and must not be retained in the scope. Scope still restores old thread-local state. Compute floating min/max during the first integer pass to remove the successful-scope second full pass, preserving original double min/max behavior. Keep insertion order/shuffling exactly identical.

**G1b next step after G1a acceptance:** Store an append-only `LatticeSummary` in Delaunay: total non-bounding count; anchor[3]; integer min/max[3]; unsigned gcd; floating min/max[3]; flag recording whether every coordinate was representable. On Build, reset then accumulate original points. Before BuildExtra, make a candidate summary and append only incoming points; derive active status using the existing rules; commit the summary together with point append. This reduces total detection work to Theta(N+total extras). Excluding the 4 big-tetra points is mandatory. The empty build has no anchor until its first real extra. One to seven points must be accumulated despite inactive fast path, so activation at count 8 is correct. Rejected off-domain extras are still appended to `points_` in current code before being skipped by `InsideBigTetra`; summary must match existing scope semantics by including them too.

**Invalidation/lifetime:** `points_` is public, copy construction/assignment exist D:241-277, and callers can mutate coordinates. An incremental cache is unsafe until every mutation path has an invalidation contract. Reset in Clean/Build; copy aggregate if points exactly copied, or rebuild/mark dirty. On external mutable access invalidate conservatively. An object-wide build generation alone does not detect arbitrary coordinate writes. Keep G1a if that contract cannot be enforced. This is a concrete reason not to jump directly to caching.

**Tests:** compare old and new scope `active`, spacing and bounds at every batch boundary and predicate results for every tested tetra. Batches: empty; 1,7,8 points; regular dyadic grids; equal coordinates; gcd initially odd then becomes a power of two; initial active set made invalid by off-grid append; span 255 and 256; original empty rank; periodic images; points outside big tetra; representability limit; repeated Clean/Build; copied Delaunay. Require identical insertion permutation and canonical topology under unchanged arithmetic. Keep robust fallback code intact.

**Counters and estimate:** `build_extra_calls`, `incoming_points`, `predicate_copied_bytes`, `predicate_summary_scan_points`, successful/failed scope count, scan/copy wall time. G1a saves 0-3% C / 0-1% L; G1b 1-10% C / 0-4% L when repeated scanning is material. These overlap.

## G2. Reuse valid cached centers during final Voronoi construction

**Observed code:** V:4419-4421 `GetRadius(i)` computes radius and `tetra_centers_[i]` only when `R_[i] < 0`; V:1489-1518 calls it while obtaining point radii, and V:3313 during queries. `SetPointTetras` invalidates `R_[i]` for changed/new tetrahedra at V:1327. Nevertheless final `BuildVoronoi` V:4263-4265 calls `CalcTetraRadiusCenter(i)` directly for every tetra touching an original point. It recomputes centers regardless of the radius cache. Multiprecision fallback V:4687-4762 uses `cpp_dec_float_50`, so redundant evaluation can be expensive for thin or nearly degenerate tetrahedra.

**Implement:** First add counters for final relevant tetra, final previously valid entries, scalar evaluations and high-precision evaluations by call site. Audit all writes to `tetras_`/point coordinates and ensure each geometry mutation invalidates radius and center together. Then use a single `EnsureTetraGeometry(i)` routine that owns both cache validity and initialization; low-risk variant uses `GetRadius(i)` in final pass after proving sentinel validity. A separate `geometry_valid`/generation flag is cleaner if negative/zero radius edge cases or geometry-only center updates would otherwise be ambiguous. Do not remove sanity checks or lower precision to make a benchmark faster.

**Subtlety:** Current direct final call refreshes center but does not update R_. The cache refactor should make radius and center a single valid pair. Reused tetra indices need invalidation even if their integer index is unchanged. Do not key validity to vector capacity or just point count. Deleted slots must remain excluded by `ShouldCalcTetraRadius`/occupancy semantics.

**Tests:** at every ghost batch compare cached vs forced recomputation for every active tetra, with robust tolerance and exact cache-validity generation assertions. Reused free slots, changed-neighbor topology, multiple batches, large coordinate translations, planar/near-planar tetra, uniform grids, refined/coarse seams, periodic images, empty ranks. Compare face geometry and total/local cell volume. A debug mode recomputing a sample of cache hits is useful during rollout. Retain original tolerance thresholds.

**Runtime estimate:** C 1-10% typical; 5-20% only when multiprecision work is frequent and already cached. L 0-3%. It cannot save more than measured redundant-center work; claim no gain if final valid-hit count is low.

## G3. Make new-tetra processing proportional to unique changed tetrahedra

**Observed code:** flip23 D:374-390 pushes tetra0, tetra1 and new slot; flip32 D:614-626 pushes both outputs; flip14 D:1209-1212 queues its rewritten tetra. Repeated flips can enqueue the same slot many times before `SetPointTetras`. V:1309-1311 shows sort/unique commented out. The actual loop V:1324-1334 loads every queued entry, invalidates its R_ before checking the `newTetra` flag, and skips duplicates only after those operations. Existing changed_tetras snapshots are captured when `newTetra` was false and serve a different purpose: preserving old adjacency to remove; do not delete them.

**Implement in two reviewable steps:** (1) measure queued IDs / unique IDs / copied old-tetra records / maximum PointTetras valence, and use sort+unique only as an experiment because sorting itself costs time and changes processing order. (2) introduce a per-slot enqueue generation/stamp and an `enqueue_changed_slot(index)` helper. Queue a slot once per adjacency-sync interval; final slot contents at sync time are what must be consumed. Newly allocated slots require explicit initialization; do not use `newTetra` alone because Tetrahedron default constructor sets it true before the first enqueue. Advancing/resetting the queue generation belongs at the exact SetPointTetras consumption point. Protect epoch wraparound. Preserve saved old adjacency snapshots before first mutation. Clearing/deleting/reusing a slot within one interval must not leave obsolete snapshot semantics.

**Tests:** alternate flip23/flip32/free/reuse sequences, a slot changed repeatedly in one batch, a slot freed and reused before sync, multiple ghost batches, zero new points. After every sync, rebuild a reference point-to-tetra adjacency from live tetras and compare set equality, absence of duplicates, and all points/neighbor indices in range. This is stronger than checking only final total volume.

**Estimate:** C 1-6%, L 0-2%, conditional on duplicate ratio. If duplicate ratio is <1.2, stamp traffic may not pay; retain measurements before proceeding.

## G4. Free-tetra structure: sorted-vector erase is the wrong hot-path primitive if free lists grow

**Observed code:** `empty_tetras_` is `boost::container::flat_set<size_t>` at D:168. flip23 obtains/erases begin D:295-298; flip14 does the same three times D:1107-1112; flip32 inserts freed slot D:631. A flat_set is sorted contiguous storage, so front erasure and interior insertion shift indices; membership queries occur for every insertion work item D:1015 and walk fallback D:1070. Some iteration/output/check paths rely on the sorted set, so a blind type substitution is incomplete.

**Implement:** After profiling, use `vector<size_t> free_slots` as a LIFO pool plus `vector<uint8_t> slot_live` for O(1) live/dead checks, with explicit `allocate_tetra_slot` and `release_tetra_slot`. Every allocation marks live before use, every release marks dead once, and releasing the same slot twice asserts in debug. Iterate slot_live for full sweeps, or maintain a separate list of slots freed since last adjacency synchronization. Audit V:1255-1285 which currently iterates all empty slots to invalidate entries. Do not compact live tetras in this phase because every neighbor/index reference would need remapping.

**Determinism:** LIFO changes integer slot reuse and can alter fan enumeration / degenerate tie behavior. If strict existing slot order matters, first use a min-heap + live mask: allocation O(log E), release O(log E), no shifts. This may save less but preserves smallest-index allocation. Keep choice behind an experimental backend until topology/conservation and deterministic-repeat tests pass. Expected performance is conditional on free-set size; E often small, and a flat_set can then be optimal.

**Test:** all allocation/release invariants, Delaunay CheckCorrect, adjacency reference rebuild, repeated builds with unchanged points, uniform/degenerate grids, mixed resolution, adversarial flip sequences. `CheckCorrect` alone is insufficient because it does not prove ghost completeness.

**Estimate:** C 1-8%, L 0-2%; negligible if E is tiny. Record sum of estimated shifted entries, max/mean E, operations, and cache-miss samples before implementation.

## G5. Range-finder wrapper owns a redundant point copy and materializes results twice

**Observed code:** `range/finders/OctTreeFinder.hpp:20` initializes `myPoints(myPoints)` into its private `std::vector<PointT>` (`:63`), even when it is passed an existing tree. `UpdateRangeFinder` V:3226 recreates this wrapper from allMyPoints every build. `OctTreeFinder::range :45-56` calls O:804-845 returning vector<IVec>, then converts every record to another vector<size_t>. Closest-in-sphere returns a heap-backed vector containing zero or one index (`finder:29-44`). The core tree query already has a templated filter, so virtual filter overhead is not the primary issue.

**Implement:** Split owning and borrowed modes explicitly: an owning point vector for iterator constructors; a stable borrowed `const vector<PointT>*` or a read-only view for existing-tree constructor, with explicit lifetime owner. Prefer retaining `shared_ptr<const OctTree<IVec>>` when the finder can outlive the member tree; use a snapshot/owner containing tree and point buffer if asynchronous query work is added. Destroy/rebind borrowed finder before `allMyPoints` is moved/replaced at next build. No borrowed pointer may survive migration/rebalance or storage mutation.

Add an OctTree query overload taking an output callback or output iterator and a caller-owned QueryScratch; have the finder directly append indices, avoiding intermediate IVec copies. Keep the existing vector-returning API as a compatibility wrapper. Add a bool/optional-index closest query internally instead of constructing vector(1), then wrap when an existing virtual API requires it. Reuse result vector capacity at batch/request level rather than global mutable state. Reservation must cap by min(request N, local count), not blindly reserve max<size_t>.

**Thread safety prerequisite:** O:261 contains `mutable nodes_stack`; const queries mutate it O:813-843 and O:860-889. Queries on the same tree are not thread-safe. Move scratch out of the tree into a per-query/per-worker object. The process-static NodePool at O:125-128 is also unsynchronized for concurrent tree allocation/deletion. Thread-local pool is not a sufficient drop-in if objects can be allocated on one thread and destroyed on another; use tree-owned arena or explicit owner/lifetime.

**Preserve semantics:** O:820 explicitly warns a leaf can represent a box for DistributedOctTree. Do not replace sphere-box intersection with a point-in-sphere test in the generic tree. Preserve radius+1e-12 wrapper expansion, filters, max-result early exit, query ordering, and ignore-set IDs. Different point ordering can alter how many ghost rounds are needed even when all query results are individually valid.

**Tests:** result sequence equality with old implementation for representative fixed queries, result set against brute force for point leaves, box-leaf distributed-tree test, N=0/1/large, empty tree, excludes-all filter, periodic image-specific ignore sets, exceptions followed by another query (scratch must be cleared), and concurrent read-query test under TSan after scratch separation.

**Estimate:** C 1-6%, L 0-3%, larger only if allocator/query counts prove it. Saved copy bytes per build approximately sizeof(PointT)*Nlocal plus intermediate query records. No node-allocation pool from scratch is required: it already exists.

## G6. Memory retention already improved; focus remaining inner capacities and face initialization

**Observed existing improvements:** `ContainerOps::conditional_shrink` at `voronoi/utils/container_utils.hpp:15-23` is disabled unless RICH_AGGRESSIVE_SHRINK. `Delaunay3D::Clean` D:1268-1275 clears vectors without releasing capacity; explicit ReleaseMemory exists D:1278-1285. OctTree has aligned pooled blocks of 4096 nodes O:53-161. Any plan that lists these as absent is stale.

**Remaining evidence:** V:1553,1560-1561 clears entire vectors of small_vectors. Although the outer allocation is retained, destruction of each inner small_vector releases any heap spill. Types at `voronoi/types.hpp:10-12` have inline capacities 24 faces/cell, 8 vertices/face, 40 tetras/point. High-valence refined/coarse cells can spill and reallocate every build. V:4255-4258 sizes face arrays to 10*Norg, constructing default elements including potentially unused small_vectors, then V:4404-4411 reduces size to actual count. Reserve is not resize; replacing this blindly would cause out-of-bounds index writes.

**Implement:** Clear inner contents while retaining existing constructed slots where the public logical size permits it; resize only when local point count changes. For face building, adopt append-oriented construction for accepted faces or a private reusable face-slot arena with distinct active count, then expose containers with correct public logical size. A straightforward safe initial change is to create one reusable scratch face and `emplace_back` accepted faces, reserve using prior accepted count plus bounded growth, and benchmark against current pre-sizing. Carry CM/volume zero-initialization semantics forward: current clear+resize gives zero values; reusing vector elements requires explicit fill for active cells before accumulation.

Do not increase inline capacities by guess. Collect valence and spill histograms (median/p95/p99/max) and sizeof each small_vector. Increasing 40 to 64 across every point can waste more memory bandwidth than it saves allocation. CSR layouts for immutable final adjacency are a separate larger experiment, not this cleanup.

**Test:** repeated oscillating N, huge seam valence, long sequence of unchanged-size builds, explicit ReleaseMemory followed by build, and lower peak memory / no unbounded retained-memory growth. Assert vector logical sizes and zero CM/volume at accumulation start. Unit-size and empty-rank builds prevent growth logic failures.

**Estimate:** C 1-5%, L 0-2%, conditional on measured spills/initialization. RSS may increase when retaining inner capacities; set a documented cap/hysteresis and expose explicit release instead of shrinking on every timestep.

## G7. Hilbert ordering has avoidable setup, full-array copies, and reentrancy hazards

**Observed code:** Every nontrivial `HilbertOrder3D` call creates `HilbertCurve3D<PointT>` at H:373. Constructor H:89-108 allocates rotations and builds invariant tables. Recursive equal-key groups repeat this setup H:417. AdjustPoints HU:57-124 splits coordinates into three vectors, makes 6 extrema passes, normalizes each vector, then combines into adjusted PointT array. `reorder` HU:150-157 copies keys; `FindEqualIndices` HU:159-217 copies sorted key array twice and builds unique list just to detect equal runs. H:340 uses function-static `recursiveCalls`, so simultaneous calls of the same template are data-racy and exceptions skip decrement.

**Low-risk implementation:** Cache an immutable function-static const HilbertCurve3D per PointT (all evaluation methods must be const and initialization must not depend on bounds). Pass explicit recursion depth through internal helper with an external public wrapper. Compute bbox in one pass over input; normalize directly into adjusted output, preserving subtraction then division (do not replace division with reciprocal multiplication if preserving bitwise keys is desired). Keep degenerate-axis handling exactly. Scan sorted keys once to record contiguous equal runs; compare this result against old function before replacing it. Avoid a full sorted-key copy by reading `keys[permutation[i]]`, if it preserves downstream contracts. Preserve old key precision, ordering algorithm, tie behavior and degenerate insertion shuffle in this phase.

**Why not simply change sorting:** H:403-420 collision remapping is complicated. An independent explicit index-permutation reference must verify the returned order is a full bijection on every collision case. Do not assert the helper is correct merely because ordinary uniform random inputs lack collisions. A collision algorithm fix is correctness scope, which should be reviewed separately from removing allocations. The exception duplicate-point search H:345-358 is O(N^2) but only on failure; do not sell it as the common-path bottleneck.

**Tests:** exact order equality for random and clustered data with no collisions, equal-key groups, duplicate points, thin slabs and constant coordinates, [0,1] boundaries, tiny batches 0..8, translations/scales, nested recursion depth and exception followed by normal invocation; TSan concurrent calls. End-to-end Delaunay topology and insertion-walk counts for any deliberate order change.

**Estimate:** C 1-8%, L 0-3%, independent of broad insertion-order research. A measured reduction of Hilbert-only time is not equal to whole-build reduction.

## G8. Avoid retracing a rejected geometric face and reallocate less face scratch

**Observed code:** A face candidate is found by scanning tetras incident to each point (V:4276-4289). `neigh_set` is updated only after the face successfully survives every cleanup at V:4375. Every early rejection (fan size <3 at V:4329; duplicate cleanup at V:4334; tiny area V:4338; CleanSameLine exception V:4365) leaves neighbor absent, so the same edge/fan may be retraced from another tetra. CleanSameLine creates a fresh `point_vec old` for every face V:994 and copies vertices V:1005; faces >8 spill. Scratch buffers for larger operations already use growing `small_vector<T,128>` at V:951-956; do not reintroduce a hard static-vector bound.

**Implement:** First count attempted edges, accepted edges, rejected-by-reason, and repeated attempts for the same pair. Add a per-point attempted-neighbor marker before fan traversal, separate from accepted output. BUT compare baseline repeated attempts: changing the start tetra rotates a face fan and numerical cleanup can behave differently. If a later attempt succeeds after an earlier rejection, deduplication would change mesh output; do not enable until that behavior is resolved or explicitly accepted with robust canonical fan ordering. Safe immediate piece: pass reusable old-vertices scratch into CleanSameLine and clear/reserve it per face, preserving algorithm and exception details.

For successful faces, a dense generation-marker indexed by point_other can replace small flat_set searches if total point count and random memory access are favorable; per-cell neighbor sets are normally small (~tens), so flat_set may be faster. Treat marker representation as benchmark option, not unquestioned upgrade.

**Tests:** regular cospherical lattices, near-coincident centers, >128-vertex faces, high refinement ratio seams, face ring rotations and reversed rings; ensure identical accepted edge set/areas and no earlier rejected fan suppresses a later accepted face. Keep existing fan traversal cap V:4306.

**Estimate:** C 0-3% typical or 2-10% for measured degenerate/high-valence repetition; L 0-2%. Scratch-only portion is likely toward the lower end. Deduplication has correctness risk despite small code size.

## G9. Thread local geometry only after data ownership is explicit

**Evidence of current serial work:** Delaunay insertion D:781-782 and D:721-723 is serial and updates shared topology, free slots, last_checked_, and member scratch arrays. Adding omp parallel for is incorrect. BuildVoronoi V:4276 onward shares face counter, appends to two cells, and writes several vectors. CalcAllCM V:3907-3940 loops faces and accumulates both adjacent cells, so parallelizing it introduces races even if each face is processed once.

**G9a first safe candidates:** Final relevant tetra geometry computations (V:4263-4265) write disjoint cache slots after tetras and points become immutable; use per-thread counters and scratch, materialize dirty-index list first and prohibit concurrent lazy GetRadius access. Face-CM projection V:4394-4401 writes disjoint Face_CM entries. One preexisting MPI rank may use 2-4 threads only if CPU affinity allocates those cores; benchmark rank/thread pairs at equal total cores. Keep MPI calls on controlling thread under MPI_THREAD_FUNNELED unless protocol explicitly needs more.

**G9b moment/face refactor:** For moments, loop active cells using FacesInCell and accumulate a private local volume/CM for each cell, then write once. This retains roughly the same per-cell pyramid work the face loop already performs twice for interior faces, but may lose shared face-vertex gathers; quantify. Preserve within-cell face and triangle order for reproducibility and the aspect-ratio recomputation V:3949-3972. For face generation, compute candidate edge ownership first, build faces into worker-private records, prefix-sum accepted counts in deterministic owner order, then fill final faces and build cell adjacency in a separate pass; no vector may be pushed by multiple threads. This is a larger change and should be last among geometry optimizations.

**Concurrency traps:** OctTree mutable stack and unsynchronized process-static pool described in G5; Hilbert static recursion depth described in G7; predicate state P:52 is thread_local, so a scope active on one thread is not automatically active in workers. Copy exact allowed predicate state into per-worker scope only when the worker operates on the same certified points; do not enable the lattice shortcut for arbitrary circumcenters/derived values. Calls outside scopes fall back to robust arithmetic; that may be correct but unexpectedly slower. Audit all functions called from a proposed loop for statics, writes to caches, exception propagation, and library thread assumptions.

**Tests:** TSan on non-MPI local kernels and separate MPI+threads correctness runs; repeat same build under 1,2,4 threads; compare canonical topology, volumes, CM, face counts, conservation; empty ranks and high-valence faces. Measure speed at fixed cores and fixed nodes, record MPI ranks/node and threads/rank, pin threads and ranks.

**Estimate:** G9a C 1-8% / L 0-2%; G9b C 5-20% / L 0-5% if geometry dominates. Both may regress when they contend with communication or require fewer MPI ranks. G2 reduces available parallel work, so evaluate after cache reuse and never add both gains.

## G10. Repeated builds: exact reuse is possible only under a complete invalidation key

**Observed code:** BuildInitialize V:1547-1567 clears the entire Delaunay and all geometry. BuildPartially and BuildPartiallyParallel rebuild active Delaunay every call (V:4131-4160 and V:2233-2234). The current code already keeps radiuses and past ghosts between builds; do not describe it as retaining nothing. No evidence in this local audit establishes how often RICH requests geometrically identical builds; root audit should instrument calling paths.

**First implement measurement:** Count identical coordinate sequences, IDs/order, ownership, boundary settings, active mask, domain/kernel state, and point-manager generation between builds. Hashes can identify candidates, but collision-safe byte/value comparison is required before exact reuse. Coordinates equality alone is insufficient because ghost owner/rank/index mappings and hydrodynamic exchange lists can change while geometry is identical.

**Exact reuse algorithm:** Preserve final mesh only when all geometry and mapping inputs are identical and no callback/kernel/decomposer state changed. Expose an explicit immutable mesh-generation token and clearly invalidate on SetBox, SetKernel, periodic changes, PreparePoints, migration/repartition, active-mask change, direct mutable point access, and new/deleted points. On any uncertainty execute full build. When communication metadata changes, geometry caching and metadata refresh must be designed separately; simply skipping Build is unsafe.

**Partial/moving updates are research after G0:** A small displacement does not prove topology unchanged or ghosts complete. Need Delaunay empty-sphere certification after coordinate updates, local affected-star/cavity retriangulation, valid boundary/ghost coverage, migrated point remapping, fallback if certification fails, and reference full rebuild every K steps in validation. Do not set a displacement threshold as a correctness substitute. Expected implementation burden is weeks/months and it should be an optional backend.

**Tests:** exact-repeat reuse then independently alter each invalidation key; ensure one changed point, one changed periodic axis, ownership reorder, active permutation, kernel mutation and ghost mapping force refresh. Compare cached/updated path to a fresh full build across hundreds of timesteps, conservation and face correspondence. Numerical tolerances must scale with box/cell geometry rather than be globally loosened to pass.

**Estimate:** exact-reuse builds 40-90% C / 10-60% L only if full geometry + suitable communication can be reused. Real moving mesh often has 0% hit rate. Certified partial update experimental 10-50% C / 0-20% L for small active fractions, unknown until implemented. State actual hit rate and amortized validation cost.

## G11. Later experiments: point-location locality and a packed tree

**Point location evidence:** Walk uses last_checked_ as its seed D:1006-1007, traverses neighbor faces D:1031-1065, and after min(100000, tetras.size()+1) steps scans all live tetras D:1066-1088. D:28-35 shuffles fixed blocks of 1024 for active lattice scope; this sacrifices some Hilbert locality to handle degeneracy. Do not remove the shuffle based only on faster random-point data.

Instrument walk-step histogram, fallback scans, insphere and orient adaptive calls, flip counts, and work per insertion. Explore smaller/larger shuffle blocks or an auxiliary spatial seed map only if walk dominates. A seed must point to a live tetra after flips/free-slot reuse; attach generation and fall back to last_checked_ when stale. Separate initial points from distant ghost batches: initial last_checked_ may be a poor start for the first ghost. Compare serial deterministic tie behavior on lattices and adversarial clouds. **Estimate:** C 0-15%, L 0-3%, regressions plausible; retain only measured improvement on the target suite.

**Packed tree evidence:** Current octree already pools allocation but still has pointer-linked nodes and recursive destruction/reconstruction each build (O:425-435, V:2135-2141). A packed immutable Morton/octree or balanced kd-tree with small leaf buckets may reduce pointer chasing and node bytes. Existing KDTreeFinder inserts incrementally (`range/finders/KDTreeFinder.hpp:61-73`), so merely switching that wrapper does not provide a guaranteed balanced tree.

Prototype a separate read-only RangeFinder backend bulk-built from point indices; keep original index identities. Benchmark leaf sizes 8,16,32,64 on fixed range/closest queries. Support exact ignore filters and conservative sphere-box boundaries. Validate query sets against brute force plus ghost completion, distribution-dependent depths, and total build+query cost. Include build/destruction time and memory; a faster query tree that takes much longer to build can lose overall. **Estimate:** C 0-15%, L 0-3% separately from point-location research, not additive. Favor G5's simpler allocations and scratch fixes first.

## Cross-cutting validation and instrumentation requirements

Existing MadVoro test harness: `source/3D/tessellation/voronoi/regression_tests/README.md`; tests `voronoi_volume`, `voronoi_volume_periodic`, `voronoi_parallel_check`, `voronoi_mock_mesh_periodic`. Do not run changed tracked binaries as proof of rebuilt source. Compile known flags/source hash and preserve raw metrics. The existing test suite needs targeted additions for any new cache/free-slot/thread/partial-build invariant; broad volume checks alone cannot locate stale geometry.

Minimum data families: uniform random; exact dyadic Cartesian lattices; perturbed lattices; clustered/nonuniform density; thin slabs; large coordinate offset; extreme refinement seams and >128 face vertices; periodic box with face/edge/corner images; physical boundary reflections; empty ranks; 1..8 local points; active subsets/permutations; repeated fixed mesh and moving mesh sequences.

For each geometry-changing optimization verify Delaunay neighbor reciprocity, live-slot references, point-to-tetra adjacency, finite/nonnegative physical cell volumes, total domain volume, face ordering/orientation, periodic translated CM identities, and ghost/global ID consistency. Canonical geometric comparison tolerates legitimate different triangulations of cospherical points but must not hide lost cells, missing ghosts or different physical faces. For mathematically unchanged allocation/copy changes require stronger sequence/order equality first.

Record phase times on all ranks (min/median/p95/max or rank-max plus imbalance), not only rank 0. V:2165,2249,2272,2283,2330 prints rank-0 elapsed values; these do not establish MPI critical-path costs. Avoid adding a collective or timer around every tetra/query. Use local aggregated counters and one controlled reporting reduction per build/report interval. Benchmark release code under production flags, retain robust predicates and normal floating semantics, warm allocation pools, repeat at least 5 times, report medians/spread and max-rank wall time, and run correctness tools on small separate debug cases.

Instrumented profiling itself has an estimated **0% direct runtime benefit and potential 1-5% profiling overhead** depending on timer/counter placement; compile-time disabling should leave approximately zero overhead. Its contribution is decision quality and avoiding misprioritization. Do not sell instrumentation as a speedup.
