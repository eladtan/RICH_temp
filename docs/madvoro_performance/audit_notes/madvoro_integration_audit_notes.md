## Evidence versus estimates

Every performance percentage below is a **planning estimate conditional on a measured affected-time fraction**, not an observed speedup. Let `f` be the affected component's fraction of baseline max-rank build time and `r` the fraction of that component eliminated: build-time reduction is `f*r`; speedup is `1/(1-f*r)`. If build time is `F` of full RICH wall time, the isolated full-run reduction is `F*f*r`. E.g. a 10% build reduction at F=0.30 gives 3% total reduction. For RICH migration/scheduling proposals, use the affected fraction of full-run time directly. Changes with overlapping components cannot have their percentages added. Include regressions and unsuccessful candidates in results.

## Proposal I1: remove per-point O(P) invariant scans

Evidence: `source/3D/tessellation/MeshDecomposer3D/load_balancing/CurveLoadBalancer.hpp:25-38` runs `std::is_sorted(boundaries.begin(), boundaries.end())` on every `getOwner(point)` before `upper_bound`. Boundaries have roughly one entry per rank. The actual ownership calculation should cost Hilbert-key conversion plus O(log P) search; release validation adds O(P). `points_manager/HilbertPointsManager.hpp:164-169` invokes this for every participating exchanged point. `environment/hilbert/HilbertCurveEnvAgent.hpp:29-31` delegates query ownership to the same function, extending the impact beyond build migration.

Implementation:

- Introduce a single boundary-install/mutation method in CurveLoadBalancer and validate sortedness once there. Restrict mutable direct access (currently public at line 21), exposing const access to consumers. Update `environment/CurveEnvAgent.hpp:34-40` to use a const accessor.
- Audit every boundary writer: HilbertLoadBalancer constructors (52,61), rebalance (175-194), rescale (218-233), changeBox (271-286), clone constructor (302), RICH restart IO constructing balancers. Existing SortHilbertBoundaries calls deliberately prevent reordered cut points after box changes; retain those semantics.
- Keep duplicate boundaries legal: they represent empty ranks. Preserve `upper_bound`, final-rank clamping, and exact equal-key ownership. Do not replace upper_bound with lower_bound or unique the boundary list.
- For source compatibility, an initial patch can compile the O(P) scan only in debug and validate all known mutation sites. Stronger production protection is encapsulation, not a mutable public vector and an untracked cached flag.
- Add a minimal ownership benchmark with fixed local point count and P=2,8,32,128,512 synthetic boundary counts (local standalone lookup, no requirement for 512 MPI ranks) plus real MPI runs. Record time per getOwner and calls per build; force observable checksum to avoid optimization removal.

Validation: malformed boundaries fail on installation in a controlled test; equal cuts and empty intervals route identically; randomized points against an old-reference owner function; box rescale/changeBox/restart and clone route identically. Verify constructor semantics before adding stricter reject-vs-sort behavior.

Estimated contribution: 50-95% ownership-lookup phase reduction **if the scan dominates that phase** at high P; possibly 0-20% at low P/Hilbert-conversion-dominated cases. If measured owner lookup accounts for 5-20% of build wall time, the high-P planning range is 2.5-19% build reduction. Full-run contribution multiply by measured build fraction F, with additional separately measured query ownership benefits. Low-risk high-priority code change, but not a claim that ownership is the current dominant phase.

## Proposal I2: avoid the root gather fallback when already-exchanged points suffice

Evidence: `MeshDecomposer3D/points_manager/PointsManager.hpp:245-268` first exchanges all participating geometry payload, computes post-exchange weight, checks imbalance, then calls `rebalance(allPoints, allWeights)` on the **original pre-exchange arrays**, then exchanges original arrays again. `balance/weightedBalance3.hpp:323-330` locally sorts keys and checks whether rank-local min/max key ranges are globally ordered. If not ordered, `weightedBalance3RootGather` gathers every `(key,weight)` pair to rank 0 (126-158) and serially sorts them. A few particles crossing old ownership boundaries can make original rank key ranges overlap even when the first exchange result follows current Hilbert rank intervals.

Small staged change:

1. Instrument ordered/fallback selection, global key count, root bytes/peak RSS, sort duration, first exchange bytes and whether a second exchange follows.
2. For **full builds under the unchanged current Hilbert indexing**, pass `result.newPoints,result.newWeights` from the first exchange to the boundary calculation. Continue to perform the final exchange on original arrays so `sentProcessors`, `sentIndicesToProcessors`, `indicesToSelf`, and original-index semantics stay aligned with RICH state migration.
3. Keep partial-build semantics unchanged initially. PointsManager's pointsExchange builds its transport list only from indicesToWorkWith (`PointsManager.hpp:288-298`), whereas original rebalance inputs may include all points; using only result.newPoints can silently change which points contribute balancing weight. The core forbids rebalance/exchange in some partial-build paths, but optimization must prove this invariant rather than assume it.
4. Guard alternate load balancers/custom indexing. The globally ordered fast path is a Hilbert property, not a universal property of arbitrary decompositions.

Validation: replay points moving across existing cuts, compare total weight and owner assignment to root-gather reference (allow defined floating accumulation differences near cuts); assert full cardinality and global IDs before and after; exercise initially empty rank, all data on root, distributed random initial inputs and large-weight outlier; verify final RICH mapping matches ORIGINAL point/cell indices.

Estimated contribution: if root fallback costs 20-70% of a rebalance event, avoiding it may eliminate 60-95% of that component, yielding roughly 12-66.5% reduction of **affected rebalance events**. This is 0% on already ordered direct-path events. If affected rebalance events are 5-20% of total build time, plausible aggregate build reduction is 0.6-13.3%; full RICH multiply by F. Retain first exchange for this staged change; do not claim its elimination too.

## Proposal I3: choose decomposition before moving full payload, then migrate once

Once I1/I2 and metrics are stable, split ownership routing/planning from payload transfer. Under the current decomposition, calculate destination rank once for each participating point, accumulate projected destination weights, and communicate weights/counts to obtain the same post-exchange imbalance metric the current code uses. Decide globally whether to rebalance. If yes, compute new cuts and destinations before sending any point/radius/CM payload. Then execute one geometry transfer and build the returned mapping directly from original indices.

Critical details:

- Simply checking local pre-move weights is not equivalent: points may cross ranks without local arrays changing length.
- Do not replace a payload exchange with an enormous dense O(P) weight vector/reduction without comparing small-local-N costs. Count/weight exchange must have a defined sparse/dense policy; the current route has dense O(P) metadata already. Initial correctness version may use dense MPI_Alltoall of a count/weight struct, then evaluate sparse transport separately.
- Since original arrays may not be globally Hilbert ordered, I2's fast route is unavailable before the first physical migration. Either exchange **only key/weight records** into current owner order for boundary calculation, or implement I4. This is still cheaper than geometry-plus-application migration but needs measurement.
- Preserve noExchange and noRebalance flag semantics; do not introduce rank-local conditionals around collective calls. Validate negative/NaN weights collectively before attempting nonmonotone prefix operations. All-zero total weight should not repeatedly trigger `0 >= tolerance*0`; define zero-work policy and existing fallback-to-unit-weights behavior explicitly.
- Keep `hadRebalance` accurate, call environment updates for the final accepted ownership, and prevent publication of intermediate send/self mapping. First-time initialization currently creates the balancer/rebalances inside `HilbertPointsManager::initialize` at 281-291; treat first build separately.

Estimated contribution: remove 50-90% of the first payload exchange **net of added planning cost**, or a regression if planning costs more. If first-exchange work is 10-30% of a rebalance event, expected saving 5-27% of that event; 0% when no rebalance and potential overhead then. If triggered events consume 5-25% of build time, aggregate 0.25-6.75% build reduction, full RICH multiply F. This overlaps I2 and I4; measure combined code, do not sum estimates.

## Proposal I4: replace unbounded root key gathering for genuinely unordered inputs

Evidence: `weightedBalance3RootGather` at lines 126,140-149 uses int byte counts/displacements and allocates global allPairs on rank 0. Beyond root memory/sort limits, large datasets risk integer overflow. The direct path at 210-319 is scalable in point data because it exchanges only cut candidates after prefix sums. Preserve it.

Recommended first scalable exact route for uint Hilbert keys: distributed key-space weighted selection. Locally sort `(key,weight)` once and prefix-sum weights. For each required cut j with target j*W/P, maintain a key interval and perform lower/upper-bound prefix lookups at candidate keys locally; reduce the resulting cumulative weights across ranks in batches; narrow to the first key whose cumulative weight exceeds the target using the existing strictness convention. Exploit shared interval prefixes across targets with histogram refinement to avoid P independent scans. Bound rounds by the actual Hilbert key bit width; keep exact tie semantics. A fixed-size coarse histogram followed by refinement of only occupied target bins can reduce communication rounds. Alternative distributed sample sort must preserve duplicate-key grouping and imbalance bounds; do not silently accept a sampled approximate partition without reporting achieved balance.

Required details for implementation plan: use the actual `curve_index_t` width, reject overflow on key+1 sentinel, preserve repeated cuts for indivisible heavy/equal keys, ensure zero-weight plateaus choose the same cut convention, collectively propagate validation failures, and keep debug root-reference only below a configurable global-count cap. Use 64-bit sizes locally and safe MPI chunking or existing large-count helpers wherever byte counts can exceed INT_MAX; casting to int is not validation.

Validation: exact comparison of old and new cuts on small unique keys away from floating target ties; weight-balance/ownership/integrity invariants when reduction order changes ties; all-empty, one populated rank, all equal key, weights=0, single huge weight, invalid weights, repeated boundaries, P>N and manufactured near-count-limit chunk paths. Unordered replay must stay bounded in rank-0 RSS as global N grows at constant N/P.

Estimated contribution: 50-90% root-fallback elapsed reduction on large N/high P when root sort/gather dominates (small N may regress); with fallback 20-70% of an affected event, 10-63% event reduction. Across an aggregate workload with fallback consuming f=0-25% of build time, 0-22.5% build reduction, full RICH multiply F. More importantly, removes an O(Nglobal) root-memory scaling limit. Do I2 first to assess residual need.

## Proposal I5: a real local-only path for suppressed exchange

Evidence: `HilbertPointsManager.hpp:153-160` and initialization 295-302 map every point to own rank when `noExchange` is true, but still invoke `PointsManager::pointsExchange`. That calls `dataExchange` at `PointsManager.hpp:300`; `source/utils/mpi_utils/exchange.hpp:60` always executes `MPI_Exchange_all_to_all`; its implementation at `mpi_alltoall.hpp:449,464` calls MPI_Alltoall and MPI_Alltoallv even for zero external payload. Core suppression flags are globally reconciled in `voronoi/Voronoi3D.hpp:2016,2020`. AMR consumes this path explicitly.

Build the result locally in **indicesToWorkWith order**: selected newPoints/newWeights/newPayloads, newIndices equal original selected indices, participating flags true, indicesToSelf equal selected original indices, empty sent processor/index lists. Preserve `onExchange(newPoints)`, `lastPoints`, environment initialization where needed and totalWeight update. Do not copy allPoints blindly because partial selection is legal. In normal exchange mode, a rank with no outgoing points may still receive, so never make the same skip based on local outgoing count alone.

Estimated contribution: 80-99% suppression-path transport elimination if timing isolates collective transport; local copy/unpack cost remains. If that transport is 0-3% of full build time, 0-3% build reduction; could be higher at high P and tiny N/P. 0% for workloads not requesting suppression. Full-run multiply F. Low-to-medium implementation risk; high value as a semantic cleanup.

## Proposal I6: make RICH decomposition switching an economic decision

The most beneficial partition for one physical kernel is not necessarily the most beneficial choice for a full timestep. Before switching from current cuts to saved per-physics cuts, estimate expected critical-rank work saved during the phase versus full switching cost: geometry migration + MockMesh + all registered state migration + downstream cache reconstruction. Require estimated savings over the reuse horizon to exceed measured switching cost with configurable hysteresis (e.g. a 1.25 safety multiplier and at least two consistent observations, values are tunables, not correctness constants). Start with opt-in telemetry and decisions logged; fallback to current policy if estimates are unavailable.

Source points: `Simulation.cpp:181-188,360-392`; `buildDataTransfer:119-128`; physical hooks beforeLB/afterLB. `lastLocalPhysicsTimes` exists at 286 and excludes the trailing barrier, while `lastPhysicsTimes` includes barrier-inflated duration and rebalance; use the former carefully as a local work proxy, separating communication wait. Do not use rank-0 elapsed only. Save decomposition versions/signatures, current ownership counts, bytes moved and prediction outcome. Candidate modes: existing per-physics switching, shared composite weights across alternating phases, or switch only if predicted net saving is positive. Compare full timesteps, not just tessellation calls.

Avoid rebuilding on exact same saved LB: pointer equality is not sufficient because GetLoadBalancer clones (`HilbertPointsManager.hpp:230-239`). Define semantic equality over type, indexing parameters, conversion box/order, boundaries, communicator identity and any custom state, plus mesh/ownership generation. Identity-point fixed-mesh skip must additionally prove same point count/order/identity/coordinates, active set, physical box/faces and periodic settings. Ownership changes invalidate geometry caches even when coordinates are equal. Never skip first build or AMR, and preserve build-generation semantics for downstream consumers.

Estimated contribution: eliminate 30-80% of unnecessary switch cost if saved cuts oscillate with little physics benefit; 0% when switching is justified. If switch+MockMesh+state movement consumes 10-40% of full RICH time, conditional full-run saving 3-32%, **minus any increased physical phase time**. This is a RICH scheduler win and should not be reported as a normal MadVoro-build speedup. Static TIMEADVANCE_2 branch alone yields no new saving.

## Proposal I7: use work estimates that predict geometry and physics, not just cell count

Uniform default cost at `CostCalculator3D.cpp:5-7` balances point counts, not variable face count, point-insertion difficulty, exact predicate frequency, ghost traffic, or radiation history workload. Begin with a cheap nonnegative model using prior-build per-cell counters: a + b*faceCount + c*pointTetIncidences + d*boundaryQueryCount + e*slowPredicates. Estimate coefficients from measured rank work, not arbitrary hand-picked units. Use prior non-wait wall cost, smooth with an exponentially weighted mean, cap anomalous weights and include a base floor. Store weights with stable IDs/migrate through the existing mappings. Do not mix wall seconds and event counts without normalization.

A single scalar weight cannot represent communication surface and memory capacity completely. Track ghost/owned ratio, peer count and peak bytes; reject proposed partitions that worsen those constraints enough to erase compute savings. Couple to I6 break-even/cooldown and report actual post-LB imbalance. Custom radiation calculators may already exist in runs, so compare against each run's effective configuration, not the base class.

Estimated contribution: upper bound for ideally reducing max/mean work imbalance L to 1 at constant total work is `1-1/L`. At L=1.3, ceiling 23.1% for the affected phase; at L=2 ceiling 50%. Plan to capture 30-70% of this headroom after overhead, so 6.9-35% affected-phase reduction for L=1.3-2, **before subtracting migration/ghost costs**. If measured compute imbalance is small or wait is network dominated, expected gain 0%. Full-build/run savings weighted by that phase fraction. Medium-to-high risk/experimental priority after telemetry.

## Proposal I8: batch RICH fields sharing a migration mapping

Evidence: `hdsim_3d.cpp:616-620` makes four sequential ownership migrations over identical sent/self mappings followed by a ghost velocity exchange. `Simulation.cpp:121-124` separately migrates extensives and cells then fills cell ghosts; each registered MigrationBuffer transfers afterward. `source/mpi/mpi_commands_3d.hpp:49-85` constructs indexed exchange buffers, compacts owned data into a fresh vector for every field (helper at 14-21), appends received data and conditionally shrinks.

Implement a field-bundle exchange plan keyed by geometry/ownership generation: compute peer counts and offsets once, serialize all needed fields for each source original index into one peer buffer, exchange once, then scatter into field arrays using the same exact order as the existing API. Keep ownership migration and ghost refresh distinct because data dependencies differ. Do not batch two stages separated by primitive reconstruction, velocity correction, source terms or flux calculations; e.g. velocity exchange before and after ApplyFix is not an obvious duplicate.

Application-level payload ownership should remain outside MadVoro. A transport transaction using mappings is less intrusive than templating MadVoro over all RICH hydro state. Preserve custom MigrationBuffer callbacks and ExchangeChain composition across multi-stage builds; migrate stable IDs alongside a heterogeneous bundle in tests. Define empty-rank field schemas without accessing cells[0]; the current adapter has default-cell fallback at 36-43 that must remain valid. Keep integer count overflow checks, per-peer order and serialization portability. Storage reuse may accompany this change but must be measured separately.

Estimated contribution: 20-60% reduction of **application field migration** time if latency/packing metadata and repeated compaction are substantial; less if raw bytes dominate. With field migration 5-20% of full RICH runtime, planning range 1-12% total reduction. This is outside ordinary MadVoro build and does not count as a core build improvement. Bundling may increase peak buffer memory: reject if unacceptable.

## Proposal I9: reduce decomposition metadata collectives and logging without changing progress

Evidence: `PointsManager.hpp:206,210` uses two reductions per imbalance check and prints every check (213-220); `reportImbalance` uses three reductions, one broadcast and two MPI_Max/Min_loc helper reductions (173-183) plus flushed output. `HilbertLoadBalancer::initializeConvertor` performs six scalar coordinate min/max reductions (134-139) then one depth reduction (152). `voronoi/Voronoi3D.hpp:2205-2211` performs two unconditional reductions purely to print post-LB max/min count. `Simulation.cpp:233,256,275` has barriers around rebalance/physics timings.

Separate diagnostics from decisions. Batch xyz minima and maxima into two 3-double reductions instead of six; preserve comm and the coordinate type assumption rather than taking &x and assuming contiguous x/y/z layout. Collect production diagnostic statistics at a configured cadence, one batched report after all asynchronous work is quiescent. Combine same-op reductions into arrays; a custom associative struct reduction for mixed sum/max/min needs a defined MPI datatype and portability tests, so first avoid unnecessary reports rather than adding complex operations. Measure removing timing barriers separately: a barrier can affect arrival skew and the currently printed meaning, so change reporting to proper max-rank reductions at a natural completion point first. Do not remove any termination/progress collective based solely on its cost.

Keep local phase durations and byte/event counters, aggregate later. `MockMesh` TIMING profiler at core lines 2642-2655 already performs maxloc and sum Allreduces inside each `_prof` call, perturbing the measured algorithm. Diagnostic builds are not neutral performance baselines. Runtime/compile-time quiet mode should avoid `std::endl` flushes in hot iterations, while retaining errors. Phase clock should use MPI_Wtime (MPI builds) or steady_clock, never assume high_resolution_clock is monotonic.

Estimated contribution: reporting/initialization collectives reduce 25-75% of their affected metadata cost; quieting logging can remove 50-99% of log-format/write time. If these combined costs are 1-8% of build time, plan 0.25-6% build reduction, full RICH multiply F; small jobs/network-synchronized runs could differ. Instrumentation-only work itself has 0% speedup goal and should add <1% production overhead when disabled/light mode. Do not add separate gains for every overlapping diagnostic collective.

## Proposal I10: compiler profile experiments with strict geometry arithmetic

The embedded RICH build is not identical to standalone MadVoro:

- `config/compiler_flags.cmake:26-31` puts `-g3`, frame pointers, disabled sibling-call optimization and `-fstack-protector-all` in all C++ builds. Release appends -O2 at 91; inherited/toolchain defaults can precede it, so inspect final compile commands, not just this variable. Intel release also uses core-avx2 at 188-190 and precise floating point at 176-182.
- `source/3D/tessellation/voronoi/CMakeLists.txt:12-33` sets standalone-only release defaults `-O2 -DNDEBUG -g1` and frame pointers. RICH embedding bypasses that block. MadVoro requires/links OpenMP (`81,145`), but linkage alone proves no hybrid parallel speedup.
- `MADVORO_USE_EXACT_INTEGER_FALLBACK` is OFF by default (42-43), propagated as a public define when enabled (147-148). Arithmetic policy is part of the reproducibility fingerprint.
- `source/CMakeLists.txt:253-294` configures dependencies and creates MadVoro target; `319-323` links it into RICH. Core geometry implementation is predominantly templated headers, so consumer translation units compile the algorithm. Setting flags only on the few exception .cpp files in libmadvoro does not control geometry code.
- `source/CMakeLists.txt:301-303` supports mixed debug translation units through config/mixed.cmake. A build named Release can still have expensive debug units; archive compile_commands.json and per-target flags.

Experiment order: clean O2 reference; O3 with existing strict FP behavior; adjust blanket stack protector to an explicitly configured performance profile only if authorized by project policy (do not silently change global default); evaluate supported target architecture, LTO and profile-guided optimization separately. Retain useful symbols/frame pointers for profiling unless their measured effect warrants a tradeoff. `-g3` primarily affects binary/build size rather than being assumed a runtime bottleneck. Do not enable `-ffast-math`, `-Ofast`, unchecked FP contraction or reassociation globally: adaptive predicates rely on arithmetic error bounds. Header predicates make isolation nontrivial; any fast arithmetic experiment requires explicit isolated non-predicate code and degenerate-case validation. Avoid mixing predicate ABI/code instantiations compiled with incompatible flags across units.

Estimated contribution: O3/architecture/LTO/PGO may yield 0-10% reduction of CPU-active geometry code, and may regress code size/cache behavior; if CPU work is 30-80% of build, 0-8% build reduction, multiply F for full RICH. Blanket protector relaxation may yield 0-5% CPU-phase reduction, typically 0-4% build under that CPU fraction, overlapping other compiler gains. Symbols alone expected runtime benefit near 0%. Do not multiply reported speedups across unmeasured compiler combinations.

## Proposal I11: trim unnecessary copies and cloned decomposition bookkeeping

Confirmed candidates: `HilbertPointsManager.hpp:172,314` copies every post-exchange point into `lastPoints`; this exists to recreate generic environment agents/clones and is not trivially removable for custom indexing. `getLoadBalancer` always clones at 230-239; `Simulation.cpp:243-246` clones/saves for each physical phase and setCurrentLoadBalance repeats it at 389. `hdsim_3d.cpp:335-340` copies full mesh including ghosts before shrinking to owned count. `mpi_utils/exchange.hpp:88-90` binds `const std::vector<T>& incomingDataOfRank`, then `std::move` into answerByProcesses (which is still a copy due to const), and separately copies into output; PointsManager currently needs output/mappings but not all duplicate answer payload representations.

Choose narrowly scoped patches: copy only owned points in hydro scratch; offer transport result mode omitting `answerByProcesses` where not consumed; preserve current generic dataExchange API for consumers requiring it; retain/map storage once instead of manufacturing multiple payload vector copies; cache a const load-balancer snapshot by mutation generation, preserving clone isolation. Do not expose live mutable saved LB state to eliminate copies because later box changes mutate stored entries (`Simulation.cpp:316-324`). Do not drop lastPoints without auditing clone/custom-agent restoration; a conditional cache for the default HilbertTree agent is a possible follow-up, not an obvious unconditional deletion.

Estimated contribution: eliminate 30-80% of the particular redundant-copy/allocation work; if those candidates total 1-5% of build, 0.3-4% build reduction, full RICH multiply F. Ghost-copy trimming benefits high ghost/owned ratio most. Snapshot cloning is O(P) and may be negligible relative to N-local work, so expect 0% when counters show low cost. Measure peak RSS as well as time.
