# Staged implementation plan: active-cell load imbalance and per-event FMM gravity cost for individual time stepping on the full-gravity TDE

## Baseline

Restart `snap_full_54` at t = 20.82, 256 MPI ranks (16 nodes × 16), 4.7 M cells. Guard floor and rate-based sink are in; the time-step collapse is fixed. Individual mode runs about **0.4–0.5×** global in sustained runs. A small event (0.1–2 % active, median 7,490 active cells) costs 2.03 s against 2.21 s for a global step, at about 1.7 events per global step just after a restart (expect 1.0–1.2 at settled cadence). Almost none of the 2.03 s scales with the active count:

| Part | Seconds | Scales with active count? |
|---|---|---|
| Mesh build | 0.64 | No: full rebuild in 26 of 38 events |
| Gravity source | 0.30 | No: FMM solve ~0.15 plus source assembly ~0.15 |
| Radiation | 0.33 | Weakly: 0.08 → 0.33 → 0.49 s with active count |
| Fluxes + updates | 0.21 | Yes |
| AMR (averaged) | 0.15 | No |
| Sync, wake, commit | ~0.3 | No |

This plan attacks the two dominant non-scaling costs — the mesh, driven by active-cell concentration (§1) — and FMM gravity (§2), with measurement gates ahead of every build step (§3), a staged, independently-gated order (§4), and labelled risks (§5).

## 1. Issue A — active-cell concentration, the decomposition, and the mesh

### 1.1 Why the current per-event rebalancer cannot fix this

Active cells cluster near the black hole and sink: the busiest rank's partial-mesh target is 30–58× the mean (`INDIVIDUAL_MESH_BUILD`), its active count up to 130× the mean (`INDIVIDUAL_ACTIVE_HILBERT_DECISION`). `build_event_mesh_impl` goes full on every rank whenever any rank's target exceeds `partial_build_fraction` of its owned cells (`hdsim_3d.cpp:1926-1941`, confirmed: `exceeds_threshold` is judged per-rank on purpose — judging the fraction on the whole mesh was measured worse, job 10199567 vs 10199440: 366 s vs 146 s over 24 events, comment at `hdsim_3d.cpp:1910-1916`). `Simulation::maybeBalanceIndividualEventByActiveBins` (`Simulation.cpp:4188`, invoked every event at `:4783`) makes a single contiguous Hilbert cut and is provably rejected: session dbacb723 established a lower bound of 211–214 for the owned-cell skew any one-range-per-rank cut can achieve here, against a limit of 2. Provably rejected rebuilds are already skipped. Tuning the closure threshold alone was exhausted — at these fractions partial ≈ full. The only lever that changes the picture is removing the concentration itself, which a single contiguous cut cannot do: any one rank owning a contiguous Hilbert range that includes the sink also owns however many active cells fall in that range, with no way to hand off only the active ones without also giving up territory elsewhere.

### 1.2 Chosen decomposition: multi-segment Hilbert ownership, built top-down by cost

**Structure.** Cut the Hilbert curve into `M ≥ P` segments (`P` = rank count). Add `std::vector<int> segmentOwner` (one entry per segment) beside `boundaries` in `CurveLoadBalancer<PointT>` (`CurveLoadBalancer.hpp:11-40`; today `boundaries` is a plain `std::vector<curve_index_t>`, no owner map). `CurveLoadBalancer::getOwner` (`CurveLoadBalancer.hpp:25-39`: unconditional `is_sorted` check, `std::upper_bound`, clamp to `size-1`) changes to index through `segmentOwner[...]` instead of returning the sorted position directly. Add a cached `boundariesValidated` flag, invalidated only on mutation, so the unconditional `is_sorted` check does not become `O(M)` per point lookup once `M ≫ P`.

**Segment construction is top-down and on-demand, not "cut equally then repair."** AREPO's own top-level tree is built by a single criterion — a node splits only because it currently violates the cost limit the assignment step later uses (`domain_toplevel.c:215`: `if(np->workload > limit || (NTopleaves < MultipleDomains*NTask && count==0))`, with `limit = 1.0/(TopNodeFactor·MultipleDomains·NTask)` at `domain_toplevel.c:177`) — there is no separate cut-then-detect-then-repair phase. RICH's segments are built the same way:

1. Start from the current `P` Hilbert segments (identity, `S=1`).
2. **Definitions.**
   - `states = individualScheduler->states()` — every owned cell's current `time_bin` (already scanned at `Simulation.cpp:4208`).
   - `count_b` = global count of owned cells currently in bin `b` (Allreduced). Bin `b` is **occupied** if `count_b > 0`.
   - Bin `b` is **constrained** iff `P·⌈count_b/P⌉/count_b ≤ active_threshold` — the true minimum achievable max/mean for `count_b` indivisible cells split evenly over `P` ranks. This is a global filter deciding which bins are worth hard-gating at all; very sparse bins are demoted to **advisory** (tracked/minimized in the assignment objective, never gate acceptance).
   - For each constrained bin, `hist[s][b]` = segment `s`'s owned-cell count in bin `b`. `cap_b = ⌈active_threshold·(count_b/P)/S·slack⌉` is the operational per-segment cap used during construction — distinct from the global filter: the filter decides whether bin `b` can ever be hard-gated; `cap_b` decides when a specific segment must split. **HYPOTHESIS, tunable at A2's gate testing:** `slack=2` default.
3. For any segment whose `hist[s][b] > cap_b` for some constrained bin `b`, split it at its own weighted median into two children and recurse, capped at depth `D`. **HYPOTHESIS:** `D ≈ log2(1/(active_threshold·min_b f_b)) ≈ 10–12` at this problem's sparsest measured band — an estimate, not yet measured against the actual sparsest occupied-bin fraction on a live segmentation run. Segment membership does not start rank-order-sorted, so the split step needs a batched, per-group ordering check before dispatching to `weightedBalance3Direct` (the `Exscan`-based path, `weightedBalance3.hpp:213-311`) versus its `weightedBalance3RootGather` fallback (`weightedBalance3.hpp:116-211`; the two are chosen between at `:310-333`, with `RootGather` also used as the unconditional fallback at `:333`) — one combined collective per round covering every currently-splitting segment.
4. Stop refining a segment once every constrained bin it holds is at/below cap, or `D` is hit (log `RICH_SEGMENT_REPAIR_EXHAUSTED`, rank-0 aggregate + one example; if this pushes a constrained bin over threshold, the acceptance test in step 6 rejects the whole plan and falls back to `S=1` — never worse than today).
5. **Assign** the final `M` segments to ranks with greedy list-scheduling (LPT): sort by priority key `Σ_b 2^(coarsest_bin−b)·hist[s][b]` descending; assign each, in order, to the rank minimizing `cost_r(s) = max((cells_r+cells[s])/C̄, max_{b constrained}(hist_r[b]+hist[s][b])/(count_b/P))`. AREPO keeps this same split between a simple primary assignment and a separate refinement pass (`domain_combine_multipledomains`, `domain_balance.c:634-1037`, vs. the separate `domain_optimize_domain_to_task_mapping`, `domain_balance.c:~1047`): the primary greedy assignment stays simple, and an optional, separate, bounded local-improvement pass runs afterward, never fused into the primary objective. **HYPOTHESIS, tunable:** cap the pass at ≤4 swap rounds, preferring to keep a segment on its current owner among near-ties.
6. **Acceptance — two independent tests.**
   - (a) Per-bin: for every constrained bin, `max_r hist_r[b]/(count_b/P) ≤ active_threshold`.
   - (b) A hard, independent safety reject, reused verbatim from the current code and never weakened into a soft objective term: `Simulation.cpp:4403-4417` already rejects a proposal outright if it does not own every rank (`reject-rebuild-empty-rank`, `:4403-4407`) or if `ownedMaxMean() > maximum_owned_cell_skew` (`reject-rebuild-owned-skew`, `:4408-4413`) — confirmed exact today, no change needed here beyond leaving it in place, independent of the per-bin test and of the assignment's soft total-cell-count term.
   - Reject the whole plan (fall back to the previous plan, or `S=1`) if either test fails.

### 1.3 When to re-decompose, and how to reverse a bad migration

**AREPO's actual criterion.** Not a single scalar "active fraction exceeded" test. `predict.c:300-322` accumulates per-bin counts as an ascending prefix sum (`tot_count_grav[n] += tot_count_grav[n-1]` for `n>0`, so `tot_count_grav[n]` is monotonically non-decreasing in `n`, i.e. the cumulative count over bins `0..n`). `predict.c:324-331` then initializes `SmallestTimeBinWithDomainDecomposition = HighestOccupiedTimeBin` and walks `n` **descending** from `HighestOccupiedTimeBin` to `LowestOccupiedTimeBin`, overwriting `SmallestTimeBinWithDomainDecomposition = n` every time `tot_count_grav[n] > ActivePartFracForNewDomainDecomp·tot_grav` **or** `tot_count_sph[n] > ActivePartFracForNewDomainDecomp·tot_sph` (`:328-330`, both a gravity and an SPH/hydro condition, joined by OR). Because the cumulative count is monotonic, once the condition is true for some `n` it remains true for every larger `n`, so the descending loop keeps overwriting until the condition first fails going down — the **final** value left after the loop is therefore the smallest (finest) bin number `n` for which the cumulative count over bins `0..n` still exceeds the threshold, not the coarsest one. `run.c:257` then gates a full decomposition on `HighestActiveTimeBin >= SmallestTimeBinWithDomainDecomposition`. When not exceeded, old domains are kept outright and the imbalance is tolerated by a cheaper, gravity-only top-leaf remap: `forcetree.c:582-598` compares `impact` against `MAX_IMPACT_BEFORE_OPTIMIZATION = 1.03` (`forcetree.h:111`) and, above threshold, calls `force_optimize_domain_mapping()` (`forcetree_optimizebalance.c`, which implements `force_get_current_balance`/`force_get_global_cost_for_leavenodes`/`force_optimize_domain_mapping`) to reassign `DomainNewTask` — used only to route tree-insertion "temporary points" — without ever touching real ownership (`DomainTask`, never written in this path) or migrating particles. Gravity cost itself is bookkept per particle as `P[i].GravCost[TakeLevel]`, accumulated during the tree walk in `forcetree_walk.c` (via the shared `CostCount` fields) and redistributed up the tree at `forcetree.c:1017-1039`, then credited by mass.

**Translation to RICH: the per-event check stays cheap; a real migration needs a measurement grounded in the actual removable cost.** `Simulation::maybeBalanceIndividualEventByActiveBins` (`Simulation.cpp:4188`, invoked every event at `:4783`, cache-gated on `active_bin_mask`) keeps its existing per-event, cache-gated cadence for the cheap check (§1.2's acceptance tests against the *current* segmentation). A real segment **migration** — building and adopting a new segment plan — is a materially more expensive, separately gated decision, and its adoption criterion must be tied to the cost segmentation is actually meant to remove, not to a rank-to-rank timing-spread proxy: §3.1 already establishes that the busiest-minus-mean gap is a heuristic that misses bottlenecks and counts unmovable work, and it fails specifically here — if every rank performs a full mesh rebuild (the dominant, admittedly-shared cost, `hdsim_3d.cpp:1926-1941`), the rank-to-rank timing spread can be small even though the removable cost (the difference between a full and a partial build) is large. The existing coarse-rebalance formula (`Simulation.cpp:5298-5327`) is unusable here regardless, since its `automatic_balance` result is unconditionally gated off by `!active_hilbert_balance` (`:5322-5325`).

**Adoption criterion — attributable, not a timing-spread proxy.** Base the adoption decision on the same mesh-build accounting the imposed-partition experiment (§1.4) already produces: for the *current* segmentation, measure the rank-max mesh-build wall time actually incurred (`INDIVIDUAL_MESH_BUILD`'s recorded `mesh_record` timings), separated into its full-build and partial-build components. For a *candidate* segmentation, project each rank's post-migration `target.size()` from its active-count distribution and the measured target-inflation ratio (§1.4), determine whether it would stay under the closure threshold on every rank, and if so, read the predicted partial-build wall time directly from the imposed-partition experiment's own measurement at a matching per-rank target fraction — an interpolation against measured points, not a further heuristic derived from timing spread. Define
`attributable_mesh_savings = cooldown_events · max(0, current_full_build_wall_time − predicted_partial_build_wall_time)`,
computed only from ranks/events where the candidate segmentation is projected to actually avoid a full build; a candidate that would still trigger full builds on some ranks contributes zero savings from those events, rather than an assumed benefit. Retain the rank busy-time spread (`maximum_event_seconds − mean_event_seconds`) purely as a secondary diagnostic, logged alongside the decision but never gating it. Adopt a newly-built segment plan only if `attributable_mesh_savings > amortization_factor · lastSegmentMigrationSeconds` (reusing `balance_options.amortization_factor`, and a persistent `lastSegmentMigrationSeconds` set to the measured wall time of the most recent segment-plan build+assign+redistribute) **and** the cooldown window has elapsed (`cooldown_events`, `Simulation.cpp:1208`) **and** both §1.2 step 6 acceptance tests pass. All quantities are Allreduced (`MPI_SUM`/`MPI_MAX`, same pattern as `Simulation.cpp:5290-5306`) before any rank branches on them, so the decision is identical on every rank by construction.

**Reversion criterion — accumulated window savings, normalized, charged consistently.** Realized savings must be accumulated over the whole post-adoption window, not compared as a per-event mean against a one-time lump cost — the two are different accounting periods, and comparing them directly can revert a partition that is still profitably repaying its migration cost. For each post-adoption window `w` of `cooldown_events` events, define
`window_savings_w = Σ_{events in window w} (baseline_cost(event) − actual_cost(event))`,
where `baseline_cost(event)` is looked up per event from the pre-adoption baseline **bucketed by event class** (active-count band, and, where cadence information from the settled-cadence measurement of §3.4 is available, by simulated-time advanced per event) rather than a single global mean, so a window with a different event-size mix or a different amount of simulated time than the baseline period is not compared unfairly. Maintain a running
`cumulative_net_benefit = (Σ_{w=1}^{k} window_savings_w) − lastSegmentMigrationSeconds`
— the migration cost charged once, at adoption, into the same ledger the accumulated savings are compared against, never re-charged per window and never compared window-by-window against a single window's raw saving. Revert to the previous segment plan (or to `S=1` if none is available) if either: (a) `cumulative_net_benefit < 0` after `k_max = 3` windows (**HYPOTHESIS/tunable**, set at A3's gate testing) — a partition that has not repaid its migration cost after three full cooldown windows is not going to; or (b) `window_savings_w < 0` for two consecutive windows — a partition that is actively making things worse, independent of whether it has already repaid its migration cost. A profitable partition whose first-window saving alone is smaller than its one-time migration cost is **not** reverted under this rule as long as `cumulative_net_benefit` is trending toward positive by window `k_max`. This is logged via `RICH_ACTIVE_HILBERT_SEGMENT_DECISION` (rank-0 + one example), reporting `attributable_mesh_savings`, `lastSegmentMigrationSeconds`, `window_savings_w`, `cumulative_net_benefit`, the diagnostic timing-spread figure, and the adopt/keep/revert action taken.

### 1.4 Cost weights — what RICH can measure per cell, and the active-count vs. target-set gap

`build_event_mesh_impl`'s `target` set (`hdsim_3d.cpp:1877-1908`, confirmed) is active cells (`context.active_indices`) **plus** a one-shell neighbour seed (`initial_seed`), a depth-two seed (`depth_two_seed`), and a cached target from the previous event (`cached_target`). The closure test (`hdsim_3d.cpp:1928-1941`) compares this full `target.size()`, not the active count, against the per-rank threshold. A rank can have a perfectly balanced active-cell count and still carry a large `target` because of its local adjacency halo or a stale cached target.

**Fix.** Track the empirically-measured **target-inflation ratio** `mesh_record.final_target/active_count` per rank (already recorded by `INDIVIDUAL_MESH_BUILD`, `mesh_record.final_target` set at `hdsim_3d.cpp:1943`). Require the segmented plan's acceptance test to bound `active_count_r · inflation_ratio_p95` against the closure threshold, not `active_count_r` alone. This is the same ratio the §1.3 adoption criterion projects candidate segmentations through.

**Per-bin weight.** Hydro/mesh weight = per-bin occupancy count from `individualScheduler->states()`, with AREPO's doubling-per-finer-bin (`domain_balance.c:203-241`, split at the `#ifdef HIERARCHICAL_GRAVITY`/`#else` branches, confirmed: `weight *= 2` walking from `SmallestTimeBinWithDomainDecomposition-1` down to `LowestOccupiedTimeBin`). **Gravity weight is explicitly excluded** from the mesh partition — Issue B covers gravity cost separately (§2), since RICH's gravity solve does not (yet) scale with rank-local active count the way AREPO's per-cell `GravCost` does; AREPO's own per-cell gravity-cost summation (`domain_grav_tot_costfactor`, `domain_balance.c:89-117`; `domain_hydro_tot_costfactor`, `domain_balance.c:129-139`) informs the *shape* of the weight-doubling table reused here, but is not itself adopted as a mesh-partition weight.

**Mandatory pre-build measurement.** Before building the assignment machinery: a cheap imposed-partition experiment — a few hand-built segment plans (2–4 segments/rank, loaded via the restart-IO field once the plumbing below exists, no assignment algorithm needed) on a short TDE window from `snap_full_54`, measuring actual per-rank closure fractions, full-build frequency, partial-build wall time as a function of per-rank target fraction (the curve §1.3's adoption criterion interpolates against), ghost/routing overhead (§5), and total wall time. `RICH_VERIFY_PARTIAL_BUILD=1` with zero `debug parity mismatch` is required as a pass/fail gate on this experiment itself, not only on the final combined build.

### 1.6 Two-mode sort semantics — a required, explicit fix

`rescale()`/`changeBox()` (`HilbertLoadBalancer.hpp:206-235,238-288`, confirmed) remap boundary values through a new box's convertor and then call `SortHilbertBoundaries` (`HilbertLoadBalancer.hpp:35-38`, a bare `std::sort`). The header comment explains why (`HilbertLoadBalancer.hpp:29-34`): Hilbert order is not coordinate-wise monotone under the remapping, so two adjacent cuts can swap; keeping the swapped order corrupts owner lookup and can route particles/ghosts to the wrong rank.

Today, with `segment == rank` (identity), a crossing during remap is harmless: rank identity is redefined purely by sorted array position, and nothing downstream depends on rank 3 keeping the *same* physical territory across a box change. A bare, unconditional sort — today's exact code — reproduces this. Carrying `(boundary, owner)` pairs through the sort unconditionally would instead make owner identity *persist* across a crossing — a genuinely different, useful property for real multi-segment ownership, but not the same behavior as today, and it would silently break the `S=1` bit-identical guarantee that global-mode and pre-segmentation individual-mode both rely on.

**Fix.** An explicit `ownerIdentityIsPositional` boolean, stored beside `segmentOwner`:
- **Positional mode** (default; the only mode used by the legacy/global-mode balancer and by individual mode before any real segmentation has been built): after any remap, discard whatever `segmentOwner` held, reassign `segmentOwner[i]=i` fresh, then bare-sort `boundaries` alone — bit-for-bit today's algorithm and today's post-crossing rank assignment, unconditionally.
- **Paired mode** (entered only once §1.2's top-down build has actually produced a genuine, possibly non-identity, possibly `M>P` assignment): sort `(boundary, owner)` tuples together, preserving which rank owns which physical range across a subsequent box change.
- The mode flag flips back to positional as the first action of the collapse-to-`S=1` migration (§1.8), before `individualScheduler.reset()`, with a freshly reassigned identity map.

**Required tests, both explicit:** (1) a box change exercised with no real segmentation ever built (positional mode) must reproduce today's exact post-crossing rank assignment, bit-for-bit; (2) a box change exercised after a genuine multi-segment plan is active (paired mode) must preserve each segment's assigned owner across the crossing.

## 2. Issue B — FMM gravity per event

### 2.1 The actual cost structure today

`FastMultipoleAcceleration3D::EvaluateIndividualTargets` (`FastMultipoleAcceleration3D.cpp:817-924`) builds `points_ = source_points`, `masses_ = source_masses` (`:869-870`) from **every** owned cell (confirmed via its caller, `ConservativeForce3D::ApplyIndividual`, `ConservativeForce3D.cpp:121-213`: `context.gravity_source_points`/`_masses`/`_ids` are assembled from all owned cells at `hdsim_3d.cpp:1526-1534`, not restricted to active ones) and calls `calculator_.solve(points_, masses_, cellIds_, ..., acc)` (`:873-874`). `DistributedFmmGravityCalculator::solve` has no target-subset parameter; `acc.size() == points_.size()` is asserted (`:881-887`). The FMM's own downward pass evaluates every occupied leaf unconditionally — `FmmPasses::downward` (`FmmPasses.cpp:63-92`) walks the whole tree in pre-order and, for every node with `particleCount() != 0` (`:83-84`), calls `evaluateL2P` on it if it is a leaf (`:88-90`), with no active/inactive distinction anywhere in that loop. Only after the full solve returns does `ApplyIndividual` subset the *result* to active cells, via `target_points`/`target_accelerations` built from `context.active_indices` (`ConservativeForce3D.cpp:188-212`) and matched back to source slots by `target_source_indices` (`FastMultipoleAcceleration3D.cpp:850-858,919-923`). Every individual-event gravity solve is, cost-wise, a full solve, restricted only at the API boundary (which target positions are requested) and not anywhere inside the tree traversal: `fmm_solve_trace` medians confirm this — an individual event with 846 median active cells costs 0.151 s total (redistribution 0.036, local traversal 0.044, LET execute 0.078) against a global step's 0.134 s at 3.1 M active (redistribution 0.048, local traversal 0.034, LET execute 0.060).

The **source side is O(N) every event**: all sources are redistributed to their Hilbert gravity owners, moments are refreshed, and the locally essential tree (LET) is exchanged. The **interaction side runs the full cached plan**: the M2L/P2P lists and the downward pass cover the whole target tree; nothing today restricts either to an active-descendant subset. Plus about 0.15 s of source-array assembly over all cells (§2.5). FMM accuracy is about 11 % RMS at order 2, theta 1.0 (pre-existing, unrelated to this work); direct-sum checks are available via `RICH_FMM_DIRECT_ERROR_SAMPLES`.

### 2.2 A design rejected outright: shipping only sources whose gravity owner changed

Centroids advance every event for **all** cells (`hdsim_3d.cpp:2715-2722`, confirmed: when `pm_.MovedPoints()`, every global cell's stored centroid is kicked by `point_velocities[global] * event_dt`, not only active cells' — the in-place per-event updates at `hdsim_3d.cpp:2662-2668,2729-2735` only refresh *active* cells' centroids from the tessellation directly, but the prediction-step kick at `:2714-2722` moves every cell's stored value), and `gravity_source_points` is reassigned as a full `O(N)` vector copy four times per event: `hdsim_3d.cpp:1526, 2668, 2722, 2735`, confirmed. The current redistribution ships each source's *current* position and mass to its owner every solve regardless of whether that owner is the same as last time (`DistributedFmmGravityCalculator.cpp:1421` calls `letPlan_.build(...)`; the redistribution path builds each particle's position from the current array every call). A source whose gravity owner is unchanged still needs its updated position/mass to reach that owner every event, because the position itself generally changes for essentially all cells, every event — the cost is payload-bound, not sort/assignment-bound. Shipping only owner-changed sources would silently use a stale position for every source that kept the same owner, which is the common case; there is no cheap fix that preserves correctness, so this option is not pursued.

### 2.3 Ranked options for the gravity solve itself

**(i-a) `solveOwned`.** `DistributedFmmGravityCalculator::solve` dispatches on `distributedOptions_.spatiallyRedistributeForGravity` between `solveRedistributed` (`:1434`) and `solveOwned` (`:2032`, builds each rank's FMM tree directly from whatever sources it already holds, no separate gravity-Hilbert redistribution). The default is `true` specifically because (`FmmDistributedOptions.hpp:109-111`, quoted): *"gravity, then return accelerations to their hydro owners. This gives the one-tree-per-rank FMM compact, balanced spatial domains even when the moving Voronoi decomposition overlaps the dense TDE core on many ranks."* — Issue A's own concentration problem. `solveOwned` is a genuinely different algorithm from AREPO-style active-target export (§2.3(ii)/(i-b) below); it still executes LET source-payload exchanges (`DistributedFmmGravityCalculator.cpp:2561`) and is not itself a communication-scaling fix — it is worth testing because Issue A's segmentation (§1) is expected to make per-rank source domains compact enough for `solveOwned`'s one-tree-per-rank design to be viable without the redistribution step's cost.

`spatiallyRedistributeForGravity` is a C++-only option today (`FmmDistributedOptions.hpp:112`); the runtime parser does not expose it (`DistributedFmmGravityCalculator.cpp:970` area, `readRuntimeSettings()`). Flipping it requires adding collectively-agreed runtime plumbing, not a bare recompile flag.

**Global-mode safety.** `calculator_` and its `distributedOptions_` are a single, shared instance used by **both** `FastMultipoleAcceleration3D::operator()` — the plain global-mode force callback, calling `calculator_.solve(...)` directly on all N cells (`FastMultipoleAcceleration3D.cpp:730-775`, `solve()` call at `:771`) — and `EvaluateIndividualTargets` (`solve()` call at `:873`). Flipping the flag at the calculator level would silently change global stepping too, violating "global-mode behaviour stays unchanged unless shown to help it too." **Fix:** `solve()` gains an optional, per-call override of `spatiallyRedistributeForGravity`, defaulting to preserve the constructed value when not supplied. `EvaluateIndividualTargets` passes the override (once proven safe); `operator()` (the global path) never passes it, so global stepping is unaffected by this feature's mere existence. Because `EvaluateIndividualTargets` is already invoked identically and collectively by every rank whenever the simulation is synchronized in individual mode, the override value is uniform across ranks by construction; this is additionally folded into `solve()`'s existing per-call cross-rank consistency check (the same style as its current `MPI_Allreduce`-based input/domain validation) as defence in depth. The combined final gate's global comparison arm stays on the original, un-flipped configuration unless a separate, explicitly labelled experiment independently shows the flip also helps global mode.

**(ii) Target-conditioning of the cached interaction plan — both the local and remote plans.** `FmmDualTreeTraversal` owns the *local* plan's `m2lPairs`/`p2pPairs` (`FmmDualTreeTraversal.hpp:37-38`) — interactions entirely within this rank's own local tree, no communication involved. `FmmLetPlan` owns a **separate** set of *remote* interaction lists — `m2lInteractions_`, `p2pInteractions_`, `m2pInteractions_` (`FmmLetPlan.hpp:211,216,218`) — built by an entirely separate process, `letPlan_.build(...)` (`DistributedFmmGravityCalculator.cpp:1421`), not by `FmmDualTreeTraversal::buildLocalPlan`. Pruning only the local plan does not shrink the remote one: they are different data structures, built by different code, and the remote lists are built once per topology and reused across solves. `FmmLetPlan`'s own "active" bookkeeping (`activeM2LInteractionIndices_` etc., populated in `beginExecute`, confirmed at `FmmLetPlan.cpp:1742-1820`) is about whether a **target node currently holds any local particles at all** (`localTree.nodes()[range.targetNode].particleCount() == 0`, confirmed at `:1756,1781,1806`) — wave/topology bookkeeping, not RICH's individual-timestep notion of "this cell is active this event." Likewise the downward pass's leaf-evaluation loop (§2.1, `FmmPasses.cpp:80-90`) has no active/inactive distinction at all today — it is the *actual, missing* leaf-level restriction option (ii) is meant to add, not something already partially done.

Target-conditioning must therefore be built in **all three** places:
- **Local plan** (`FmmDualTreeTraversal::buildLocalPlan`/`runLocalPlan`, `FmmDualTreeTraversal.hpp:57-77`): skip M2L/P2P pairs and L2L/L2P propagation into subtrees with no active descendant leaf.
- **Downward evaluation** (`FmmPasses::downward`, `FmmPasses.cpp:80-90`): skip `evaluateL2P` for leaves with no active descendant, mirroring the `particleCount()==0` skip already present at `:83-84`.
- **Remote plan** (`FmmLetPlan::build` and its interaction-list construction, `FmmLetPlan.hpp:194-204` for the admissibility tests, `FmmLetPlan.cpp:1112-1136` for the subscription-set construction confirmed to build directly from `m2lInteractions_`/`p2pInteractions_`/`m2pInteractions_`): restrict to target nodes with an active descendant, not the whole target tree with a later wave/non-empty-node filter. This touches the traversal that decides which remote interactions exist at all, the subscription-set/wave-sizing derivation that follows from them, the per-wave execution ranges, and — critically — the LET plan's own reuse/cache-validity check (analogous to `localPlanReusable` for the local plan) must also be keyed on the active-target set, or a stale remote plan built for a previous event's active set silently under- or mis-evaluates the current one.

**Near-field particle transmission is a design choice, not a physical necessity.** AREPO's own gravity walk avoids shipping raw particle data for near-field (P2P) interactions entirely, via **owner-side evaluation**: a particle that drifted into another task's domain is sent to that task, which performs the force computation itself and sends back only the resulting force (`gravtree.c:329-336`, confirmed doc-comment: "Particles which drifted into the domain of another task are sent to this task for the force computation. Afterwards the resulting force is sent back to the originating task."). RICH's current design instead **imports** remote source data (moments for M2L/M2P, raw particles for P2P) and computes locally — a genuine architectural choice (pull-and-compute-locally vs. push-and-compute-remotely), not a physical necessity of the near-field term itself.

**(i-b) Pull vs. push, once (ii) is built.** Once (ii)'s full scope (local plan, downward evaluation, and remote plan target-conditioning) lands, RICH's pull/subscribe architecture achieves "communication scales with the active target count" for its own design. The remaining, narrower, genuinely open question is whether that pull design, once correctly conditioned, is meaningfully worse than AREPO's push/owner-side-evaluation design for the same (now properly reduced) active-target set.

Both sides must be measured or estimated in comparable units, and the "exposed communication" metric must actually exclude computation:

- **Pull (RICH, measured, not estimated), after (ii) lands:** the metric to use is `letExchangeSeconds` (`FmmLetPlan.cpp:2599-2603`, confirmed by its own comment: *"Report only exchange work exposed on the critical path: preparation, residual wait, and decode. Transfer time hidden by local traversal is intentionally excluded from this phase timer."*), **not** `letExecuteSeconds` (`DistributedFmmGravityCalculator.cpp:2571`: `stats_.letExecuteSeconds = letBeginSeconds + elapsed(letFinishStart)`, a wall-clock span that also contains the M2L/P2P/M2P kernel compute, i.e. it is not a pure communication figure). Report both, but only `letExchangeSeconds` is the pull-side term entered into the push/pull comparison; `letExecuteSeconds` (and, as a rough proxy for kernel compute alone, `letExecuteSeconds − letExchangeSeconds`) is reported separately as the total critical-path cost, never conflated with the communication comparison. Extend `stats_` to report, at the 846-active-cell class: `letExchangeSeconds`, the plan/memory footprint (`letPlanBytes`, `DistributedFmmGravityCalculator.cpp:2589`), and payload bytes split by kind (multipole vs. particle — the two kinds are already distinguished in the subscription-set construction, `FmmLetPlan.cpp:1116-1136`, and their distinct wire sizes are already computed for wave sizing, `:1153-1174`) — all restricted to active targets once (ii)'s remote-plan scope is built.
- **Push (AREPO-style, necessarily a HYPOTHESIS until built, but with its *inputs* measured):** directly instrument **target-to-owner incidence** — for each active target, the distinct set of remote ranks it needs data from, deduplicated per target, walked directly from the (now correctly active-conditioned) `m2lInteractions_`/`p2pInteractions_`/`m2pInteractions_`'s `(targetNode, sourcePatch.ownerRank)` pairs (all three interaction kinds, including M2P, not just M2L/P2P). Charge **latency per distinct destination peer actually contacted in a wave**, not per target–owner pair: AREPO itself batches every particle/node destined for a given peer into one `MPI_Sendrecv` pair per `(ngrp, recvTask)` combination (`generic_comm_helpers2.h:373-397`, confirmed: one `Sendrecv` per `recvTask` carries `Send[recvTask].Count`/`Recv[recvTask].Count` records for every particle routed to/from that peer in the cycle), so the comparable push-side cost model is `n_distinct_peers_per_wave × round_trip_latency + total_bytes_to_that_peer/bandwidth`, summed over waves and peers — not `n_active_targets × n_distinct(target,owner)` charged independently per target, which would overcount latency whenever multiple targets share a destination peer within the same wave. Use the measured incidence to derive both the deduplicated peer/wave count (for latency) and the total byte volume (for bandwidth), with latency/bandwidth taken from existing MPI micro-benchmarks if available, otherwise explicitly labelled HYPOTHESIS end-to-end.
- **Owner-side work, not just bytes.** A push design moves *computation*, not just data, onto the source-owning rank. Estimate the owner-side compute term as `n_interactions_assigned_to_owner × mean_per_interaction_kernel_cost`, using `letExecuteSeconds − letExchangeSeconds` (per interaction handled locally today) as a rough per-interaction compute proxy, explicitly labelled HYPOTHESIS where it is extrapolated to a different (owner-side) execution context. Add this term to the push exposed-time estimate for whichever rank would be the busiest owner. If `n_distinct(target,owner)` pairs concentrate on a few ranks — plausible, since those ranks are the same ones that hold the TDE's dense core mass — a push redesign could reintroduce a load-balance problem on the gravity side, symmetric to Issue A's mesh problem. Check this with a histogram of `n_distinct(target,owner)` grouped by owning rank before any go decision.
- **Go/no-go:** pursue an owner-side-evaluation rewrite of `FmmLetPlan` (a genuine, high-risk protocol change) only if (a) the HYPOTHESIS push exposed-time estimate (peer/wave-batched latency + bandwidth + owner-side compute) is lower than the measured pull `letExchangeSeconds` by a wide, defensible margin (≥2×, given the estimate's own uncertainty and the rewrite's risk), **and** (b) the owner-side-work histogram does not show new concentration on a small set of ranks. Otherwise, the target-conditioned pull design of (ii) is kept as sufficient and no further gravity-communication rewrite is pursued.

**(iii) Incremental source updates — later, accuracy-gated.** Update only tree nodes whose cells moved/changed mass noticeably; keep far, slow nodes across events. An algorithmic change with an accuracy trade-off against the FMM's pre-existing ~11 % RMS error at order 2/theta 1.0 — gate with `RICH_FMM_DIRECT_ERROR_SAMPLES`. Pursue only if (i-a)+(ii) together fall short of parity.

### 2.4 (iv) `HIERARCHICAL_GRAVITY`-style split — full analysis

**The actual mechanism.** AREPO walks time bins in a loop. On the *first* half-kick, particles cascade downward one bin at a time from `HighestSynchronizedTimeBin` while `test_if_grav_timestep_is_too_large` demands it (`do_gravity_hydro.c:176-208`, confirmed: loop from `HighestSynchronizedTimeBin` down, one-bin cascade via `timebin_move_particle`). On the *second* half-kick, bins are walked in **ascending** order, `timebin = 0` up to `HighestActiveTimeBin` (`:366`, comment at `:365`: "in inverse sequence so that we end up getting the cumulative force at the end"), and for each synchronized bin, `timebin_make_list_of_active_particles_up_to_timebin(&TimeBinsGravity, timebin)` (`:371`) builds a **cumulative** active list of every particle in bins **≤** `timebin` — not just particles active this specific bin. `compute_grav_accelerations(timebin, ...)` (`:378`) then solves gravity for that cumulative set.

Define `K_b` as the kick factor for level `b` — `get_gravkick_factor(tstart,tend)` under comoving integration, or `(tend-tstart)·Timebase_interval` otherwise (`:391-394`), evaluated over the interval half-width `2^b/2` centered at `Ti_begstep[b]`. The applied kick at level `timebin` is:
- `K_timebin` alone, when `timebin == HighestActiveTimeBin` (the top level: `:396`'s condition is false, no subtraction);
- `K_timebin − K_{timebin+1}`, when `timebin < HighestActiveTimeBin` (`:396-407`, confirmed: `ti_step`/`tend`/`tstart` are recomputed for level `timebin+1` — **the next *coarser* level**, encountered *later* in this same ascending loop, not the finer level already visited — and its kick factor is subtracted: `dt_gravkick -= get_gravkick_factor(tstart, tend)` or the non-comoving equivalent).

This is a telescoping difference: writing the coefficients as `K_b − K_{b+1}` for every level below the top, plus `K_B` at the highest active level `B = HighestActiveTimeBin`, each level's *own* contribution is isolated from the coarser overlap that level `timebin+1` will separately supply when the ascending loop reaches it — reconstructing the correct cumulative impulse without double-counting.

**What this means physically.** Because the cumulative set is "bins ≤ timebin," a *coarse* (slow) bin's rare update recomputes forces including every faster particle that has moved since — correct and necessary, since fast/near particles can dominate a slow/far particle's force. But a *fine* (fast) bin's frequent update, most steps, only includes other fine-bin particles as sources — the contribution from coarser (slower) particles is refreshed only at the slow particles' own natural cadence, not every fast step. This is the actual approximation: fast particles' forces from slow/distant sources go stale for up to that source's own bin interval, accepted because bins are chosen to track genuine dynamical timescales (a slow particle's contribution changes slowly by construction).

**`PMGRID`/long-range force (`do_gravity_hydro.c:356-363`) is an entirely separate, optional, `#ifdef`-gated mechanism** — one global long-range particle-mesh kick applied to all particles when a PM step is due, independent of and orthogonal to `HIERARCHICAL_GRAVITY`. It has no logical connection to why the hierarchical scheme's active-only tree walk is valid; a separate long-range solve does **not** justify or backstop omitting inactive sources from the hierarchical tree walk itself.

**`ALLOW_DIRECT_SUMMATION`/`DIRECT_SUMMATION_THRESHOLD=3000`.** The gating lives in `accel.c:103-106` (`if(TimeBinsGravity.GlobalNActiveParticles < DIRECT_SUMMATION_THRESHOLD) gravity_direct(timebin); else <tree walk>`, threshold defined in `main/allvars.h:246`), and `gravity_direct()`/`gravdirect.c:92,123,150` packs and evaluates the **already bin-cumulative-restricted active list** that `compute_grav_accelerations` was called with (`do_gravity_hydro.c:378`) as its source set — i.e. it substitutes O(n²) direct summation for O(n log n) tree traversal on the *same* restricted set `HIERARCHICAL_GRAVITY` already defines, not a further restriction on top of it. **It is therefore only physically valid together with the whole hierarchical bin-cumulative scheme, not as an independent addition to RICH's current (non-hierarchical) full-source-every-event architecture.** Reusing "direct sum below 3000 active, sources = active only" in RICH today, without adopting bin-cumulative restriction, would drop exactly the inactive/coarser contribution RICH currently computes correctly (expensively) via full redistribution + tree, and would be a physics bug, not an optimization.

**Interaction with RICH's per-cell half-kick cache.** RICH's `gravity_half_kick_pending` (single bit) / `cached_acceleration` (single `Vector3D`) (`IndividualTimeStep.cpp:217-218,377-378,481-487`, confirmed: one bit and one vector per cell, serialized/restored as flat arrays) implement a flat, single-tree "first half from cache": one acceleration value, one pending flag, computed from one (global) tree. A genuine `HIERARCHICAL_GRAVITY`-style adoption would need each cell's cached state to record **which cumulative bin level** its last partial kick was computed against, and the associated already-applied kick factor, to correctly compute the next difference kick — a strictly larger, per-bin state, not a drop-in reuse of the existing binary flag. **Until that redesign is separately scoped and reviewed, RICH's existing half-kick cache must be treated as incompatible with any hierarchical-tree adoption and must not be reused as-is.**

**Physics acceptability near the TDE sink — open, not resolved.** The sink's dominant force on near-vacuum guard-floor cells may come primarily from the central black hole (an external point-mass potential, likely evaluated exactly every step regardless of any FMM bin-tree scheme, `TDE_force.hpp`), in which case the hierarchical scheme's staleness risk applies only to the *cell-cell self-gravity* component, which may be subdominant there. This is a HYPOTHESIS, not yet checked, and must be verified — which fraction of a guard-floor cell's acceleration is external-potential vs. FMM self-gravity — before any A/B is attempted. **Do not pursue the hierarchical-tree piece before both this check and the cache-redesign above are done.**

### 2.5 The ~0.15 s source assembly

`hdsim_3d.cpp:1526-1534` rebuilds `gravity_source_masses`/`gravity_source_ids` from every owned cell every event; `gravity_source_points = individual_centroids_` is reassigned as a full `O(N)` vector copy four times per event (`hdsim_3d.cpp:1526, 2668, 2722, 2735`, all four confirmed). `individual_centroids_` itself is a persistent, canonical-count-sized member (declared `hdsim_3d.hpp:320`, cleared at `:215,235`), refreshed selectively — only active cells' entries are overwritten from the tessellation within an event (`hdsim_3d.cpp:2662-2668,2729-2735`, gated by `context.isActive(global)`), while the prediction step advances *every* cell's stored centroid by its point velocity when `pm_.MovedPoints()` (`:2714-2722`, confirmed, no active gating there). Its lifecycle already has a single invalidation choke point: `hdsim_3d.cpp:1516-1524` detects any size mismatch against the current `canonical_count` (which changes under any topology change — AMR split/merge, or a per-rank ownership change from rebalancing) and unconditionally resizes and fully rebuilds every entry from `tess_.GetCellCM(global)`.

**Fix, scoped to mass/ID only, not position.** Because centroid *positions* genuinely change for effectively all cells every event (via the prediction-step kick above), a dirty-bit optimization on position would save little; the assembly cost worth cutting is the masses/IDs rebuild (`extensive_[global].mass`, `cells_[global].ID`, stable for a cell unless its mass changes from accretion/feeding physics) and the redundant repeated full-array reassignment of `gravity_source_points` to the same `individual_centroids_` object within one event. Add two new persistent members at the same scope as `individual_centroids_` (`hdsim_3d.hpp`, beside line 320): `last_source_mass_`, `last_source_id_` (both canonical-count-sized), plus a `source_mass_dirty_` bit vector. **Resize and reset all three to fully dirty inside the exact same branch that already invalidates `individual_centroids_`** (`hdsim_3d.cpp:1516-1524`), so any topology change (AMR, migration) automatically forces a full resend with no separate invalidation logic to keep in sync — the worst case on a missed edge case is an unnecessary full resend, never stale data. The existing centroid-clearing hooks at `hdsim_3d.hpp:215,235` are the acceptable invalidation path for the equal-count-migration case, exactly as they already are for `individual_centroids_` itself; this plan does not change that behavior, only extends it to the two new arrays.

**Buffer ownership and the context-population contract.** `last_source_mass_`/`last_source_id_` are simulation-owned, canonical-count-sized members with the lifetime and invalidation described above. `IndividualStepContext` itself keeps its existing contract unchanged: `prepareEvent` (`IndividualTimeStep.cpp:403-417`) still constructs a fresh, empty `result` every event, and `context.gravity_source_masses`/`context.gravity_source_ids` are still freshly resized every event (`hdsim_3d.cpp:1527-1528`) — resizing a freshly-constructed empty vector value-initializes every new entry to zero, so simply skipping the write for an unchanged cell would silently leave that cell's mass/ID at zero, not its real retained value. **The fix is therefore not to skip writes into an otherwise-untouched fresh array; it is to seed the fresh array from the retained one before the assembly loop narrows to the dirty subset:** immediately after `resize`, bulk-copy `context.gravity_source_masses = last_source_mass_` and `context.gravity_source_ids = last_source_id_` (a plain `std::vector` copy-assignment over the full canonical count — cheap and contiguous, no struct access), then run the assembly loop only over the subset of cells whose `extensive_[global].mass` differs from `last_source_mass_[global]` (a single-field comparison, cheaper than touching `cells_[global].ID`'s larger struct unconditionally), overwriting both `context.gravity_source_masses[global]` and `context.gravity_source_ids[global]` for exactly that subset, and updating `last_source_mass_[global]` to the new value so the next event's comparison is correct. `last_source_id_` never needs a per-event update outside the full-dirty reset, since a stable global index's ID cannot change without a topology change (which already forces the full-dirty reset).

The saving this yields is real but smaller than a naive "skip unchanged cells" framing suggests, and must be measured, not assumed: it is (the original full loop touching `extensive_`/`cells_` for every cell, including the `static_cast` on `cells_[global].ID`) **minus** (one full-array vector-copy of two flat arrays, plus a single-field comparison loop over the full count, plus the assembly loop restricted to the dirty subset). Stage 0/B1's timing experiment (§3.3) must instrument all of these sub-costs — the bulk copy, the comparison loop, the dirty-only assembly, and the four-times point-reassignment collapse — separately, so the net saving is confirmed rather than assumed; if the bulk copy plus comparison loop turns out not to be cheaper than the original full touch (e.g. because `extensive_`/`cells_` access is not in fact the dominant cost within the 0.15 s), B1 is not adopted regardless of how it is structured.

**Required tests.** (1) Bit-identical accelerations on a forced-all-dirty run (regression baseline, no skipping exercised). (2) A **mixed changed/unchanged run** — some owned cells' masses forced to change between events, others not — compared against full assembly with skipping disabled, verifying that both the bulk-copied unchanged entries and the freshly-written dirty entries produce identical final accelerations, not just the trivial all-dirty case. (3) A run that forces a topology change (AMR split/merge, or a rebalance that changes a rank's `canonical_count`) mid-run, verifying the dirty tracking resets to fully-dirty at that boundary and no stale mass/ID value from before the change is reused after it.

## 5. Risks and open physics questions

- **HYPOTHESIS.** The 2.0 s → 1.3 s per-event estimate needs re-measurement against the target-inflation ratio (§1.4), not just active-count balance.
- **HYPOTHESIS.** Fragmented ownership's own routing/build cost could eat into or exceed Issue A's savings at high `S`; sweep `S` empirically before picking a production default.
- **HYPOTHESIS.** Radiation's growth with active count (0.08→0.33→0.49 s) is unattributed between concentration and genuine active-count scaling.
- **RISK.** §1.3's adoption criterion projects a candidate segmentation's partial-build wall time by interpolating the imposed-partition experiment's measured curve; if that experiment only samples a few coarse points, the interpolation for an arbitrary candidate's per-rank target fraction is itself a source of error. A1's imposed-partition sweep must cover enough points to make this interpolation defensible, not just satisfy the closure-fraction gate.
- **RISK.** Issue B(i-a)'s viability is gated on Issue A actually producing compact per-rank mesh domains; measure directly (Stage B3), don't assume success follows automatically from A.
- **RISK.** The remote LET plan and the downward-evaluation pass are both separate from the local plan and each need their own target-conditioning, their own reuse/cache-validity fix where applicable, and their own measurement (§2.3, Stage B2). Treat B2 as the larger of the two FMM-side stages, not a small follow-on to (i-a).
- **RISK.** With the incremental-redistribution fallback rejected outright (§2.2) and (i-b) scoped as "measure after B2, then decide" rather than assumed-free, there is no cheap fallback if B1–B3 fall short beyond the narrowly-gated B4 rewrite — the combined final gate should not assume success without the Stage 0/B2 measurements landing favorably.
- **RISK.** The reversible migration decision (§1.3) adds its own measurement overhead (tracking accumulated window savings over a multi-window post-adoption period); this bookkeeping must itself stay cheap enough not to erode the savings it is meant to protect — verify at A3's gate.
- **OPEN PHYSICS QUESTION.** Whether a guard-floor sink cell's acceleration is dominated by the external black-hole potential or by FMM cell-cell self-gravity is unmeasured and gates any hierarchical-tree work (§2.4).
- **RISK.** Any direct-summation shortcut must retain the full source set; AREPO's own active-sources-only direct routine is valid only inside its bin-cumulative restriction, which RICH has not adopted, and copying it independently would be a physics bug (§2.4).
- **RISK.** The collapse-to-`S=1` migration inside `adaptiveEnterGlobal` is a new collective on the exact code path where two rank-local gates caused MPI deadlocks this week; must use the same MPI_LAND/MPI_MIN agreement discipline already fixed there.
- **RISK.** Box growth changes the gravity/mesh cost profile ~10×; both Issue A's segment plan and Issue B's per-cell/plan state must be invalidated on `NotifyDomainChanged()` (`Simulation.cpp:2209-2228`), exactly as the adaptive controller already does for its `tau` baselines.
- **RISK.** A push/owner-side-evaluation rewrite, if ever pursued, could concentrate gravity *computation* (not just data) on the same hot ranks Issue A already fights on the mesh side — explicitly checked before any go decision (§2.3), not assumed away.
